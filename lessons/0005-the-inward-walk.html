The Inward Walk

Every sweep so far has moved in one direction. This one starts at both ends and walks in — and the thing that licenses it is not a predicate, it's the array being sorted.

Same minimal-pair move as last lesson. Two problems, same ask, one fact differs.

LeetCode 1, Two Sum. Given an array of integers and a target, return indices of the two numbers that add up to target.
LeetCode 167, Two Sum II. Given a 1-indexed array of integers already sorted in non-decreasing order and a target, return indices of the two numbers that add up to target — using only constant extra space.

The fact is sorted. You already have a tool for the first version — it's the complement lookup from lesson 0004, restated for pairs instead of prefixes: sweep once, and at each value ask a hash map whether you've already seen target − nums[i]. O(n) time, O(n) space, and it does not care about order at all.

Sortedness is what buys you the O(n) time without the O(n) space — but only if you use it correctly, which means giving up the hash map entirely for a pair of indices that walk toward each other.

The move, and the argument for why it's safe

Start left at index 0 and right at the last index. Look at nums[left] + nums[right]:

  • Too small → you need a bigger sum. nums[right] is already the largest value still in play, so the only lever left is nums[left]. Advance it: left += 1.
  • Too big → symmetric. nums[left] is already the smallest value still in play. Pull right in: right -= 1.
  • Equal → done.

The move is not a heuristic; it's provable, and the proof is the whole licence check. Suppose nums[left] + nums[right] < target and some valid answer pair (i, j) exists with i < j. Could i = left? Then j would have to be some index ≤ right — but nums[right] is the largest value at or before right, and nums[left] + nums[right] is already too small. Pairing left with anything smaller only makes the sum smaller still. So left cannot be part of any valid pair that also respects right, and discarding it loses nothing. The mirror argument discards right when the sum is too big.

This is the same clause you already met in the glossary's two pointers entry, just read from the other end: "movement in one direction should not reverse the effects of movement in the other" (USACO Guide — Two Pointers). Advancing left can only raise the sum; pulling in right can only lower it. Neither move can undo what the other was trying to fix, which is exactly what makes throwing an index away for good a safe thing to do. 
def two_sum_sorted(nums, target):
    left, right = 0, len(nums) - 1
    while left < right:
        s = nums[left] + nums[right]
        if s == target:
            return (left, right)
        if s < target:
            left += 1
        else:
            right -= 1
    return None

O(n) time — each step retires one index for good, so there are at most n steps total, the same amortised argument as lesson 0003's shrink loop. O(1) space: no map, just two integers.

How badly does it fail if the array isn't sorted? Running two_sum_sorted against a brute-force existence check, on sorted small arrays it disagreed 0 times in 30,000 trials. Feed it the same arrays unsorted and it disagreed on 28.6% of them — sometimes reporting no pair exists when one does, sometimes returning indices that don't sum to target at all. The proof above used "largest value at or before right" as a fact about the array. Unsorted, that fact is just false, and the licence check fails at the first line.

The invariant, stated once

Same discipline as lesson 0003: write the sentence that's true every time control reaches the top of the loop, rather than trusting the shape of the code to carry it.

The invariant

If a valid pair exists in nums, it lies within nums[left..right], inclusive of both ends.

Every step either finds the pair or narrows that range by exactly one end, never both, and never the wrong one — that's what the proof two sections up actually established. The loop ends either by returning early or by left and right meeting, at which point the range holds at most one element and no pair fits inside it.

Two ends versus one direction

 Both are two pointers in the glossary's sense — each index visited at most once — but they're licensed by different facts about the input, which is why mixing them up produces confidently wrong code rather than a crash.

The licence generalises further than "sorted". Container With Most Water (max area between two lines, width × shorter height) is solved the same inward-walk shape on an array that is not sorted at all. The argument there is different — at each step you can prove the shorter line can never be part of a better answer than the one you already have at this width, so you move it, never the taller one. Same shape, same "throw an index away for good" discipline, but the provable-discard argument is bespoke to the problem rather than "the array is sorted". Worth a lesson of its own; filed for later.

Saying it out loud

"n is 3e5, sorted, asking for a pair. A hash-map complement lookup
 from lesson 0004 already solves this in O(n) time and O(n) space,
 regardless of order.

 But it's sorted, and that's a stronger fact than 'seen before' - it
 tells me which end is extreme. So I'll walk in from both ends instead:
 if the current pair sums too low, right is already the largest value
 left in play, so left is the only lever - advance it. Too high, the
 mirror move on right. Either move only discards an index once I can
 prove no valid pair needs it.

 O(n) time, same as the map, but O(1) space - and the win is provable,
 not assumed, because the discard argument only holds under sortedness."

The sentence worth saying to an interviewer is the middle one: not "I'll use two pointers" but "sortedness lets me prove which index to throw away, so I don't need to remember what I've seen." That's the same trade-off-analysis move lesson 0004 asked for, aimed at a different fact about the input.
