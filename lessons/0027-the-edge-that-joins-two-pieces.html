The Edge That Joins Two Pieces

Lesson 0021 answers “how cheaply can I reach each node from here?” This lesson answers a different question that reads almost identically on the page: “how cheaply can I keep everything connected?” The two produce different trees, and the cheaper-to-reach one is the wrong answer to the second question about six times in ten.

The tell is a weighted undirected graph, the words “connect all” or “minimum total cost”, and no starting node named anywhere in the problem. That missing start is the giveaway: a shortest-path question has to say from where, and this one can't, because nothing is being travelled. LeetCode 1584, Min Cost to Connect All Points: given points on a plane, pay the Manhattan distance to lay a wire between two of them, connect them all for the least total cost. CSES 1675, Road Reparation: repair the cheapest set of roads leaving “a decent route between any two cities”, or report that none exists. The object you are being asked for is a minimum spanning tree: “a spanning tree such that the sum of edge weights are minimized” (USACO Guide).

Why Dijkstra's tree is not this tree

Dijkstra (lesson 0021) also finishes holding a tree: the edge each node was finally settled through. It is tempting to hand that in. Three nodes are enough to show it is a different object.

A triangle: three nodes, three edges. Both trees below are correct — for different questions.
TreeEdges chosenTotalWhat it is optimal for
Minimum spanning tree 0–1 (4), 1–2 (7) 11 Total wire needed to connect all three
Dijkstra's tree from node 0 0–1 (4), 0–2 (9) 13 Shortest trip from node 0 to each node

The edges are 0–1 = 4, 1–2 = 7, 0–2 = 9. Dijkstra refuses the 7 because reaching node 2 through node 1 costs 4 + 7 = 11, and the direct 9 is cheaper — which is the right call for its question. The spanning-tree question never asked about trips from node 0, so the 9 is simply two units of wire wasted. Neither algorithm is wrong; they optimise different totals, and only one of them is the total the problem asked you to minimise.

The licence: the cheapest edge leaving a piece is always in the answer

Every pattern in this course earns its halving or its greediness from one provable statement, and here it is the safe edge lemma. Take the forest you have built so far; an edge is safe if it is “the minimum-weight edge with exactly one endpoint in some component” of that forest, and useless if “both its endpoints are in the same component” (Erickson, Algorithms, ch. 7). The lemma is one line: “The minimum spanning tree of G contains every safe edge.”

The proof is an exchange argument, the same instrument lesson 0023 uses to separate a greedy that works from one that doesn't. Suppose some spanning tree T leaves out the lightest edge e crossing out of a set S. T still connects e's two endpoints by some path, and that path has to cross out of S somewhere, on an edge e'. Swap them: “adding e to this forest gives us a new spanning tree T′ = T − e′ + e”, and since e was the lightest crossing edge, T′ “has smaller total weight than T”. So T wasn't minimum. Leaving out a safe edge is never free.

That is the whole permission slip for being greedy about weight. The remaining question is only bookkeeping: which edge is safe right now, and how do you tell cheaply?

Kruskal: sort once, and ask “different pieces?” once per edge

Scan edges from lightest to heaviest. “Because we examine the edges in order from lightest to heaviest, any edge we examine is safe if and only if its endpoints are in different components of the forest” (Erickson) — so the entire safe/useless test collapses into one question you already know how to answer in near-constant time: are these two nodes in the same component? That is lesson 0016's union-find, and this is the problem it was built for. cp-algorithms states the same pairing: “if the ends of the currently picked edge belong to different subtrees, these subtrees are combined” (Kruskal's algorithm).

def min_spanning_tree(n, edges):          # edges: list of (weight, u, v)
    uf = UnionFind(n)                     # lesson 0016, unchanged
    total, chosen = 0, []
    for w, u, v in sorted(edges):         # lightest first - the only sort
        if uf.union(u, v):                # True only if u, v were in different pieces
            total += w
            chosen.append((w, u, v))
            if len(chosen) == n - 1:      # a spanning tree has exactly n-1 edges
                break
    return total, chosen

The shape is lesson 0010's skeleton — sort once, sweep once — with the sort key being edge weight and the per-item decision being a component test instead of an overlap comparison. Cost is O(E log E) — “since the most expensive operation is sorting the edges” (USACO Guide). Erickson puts the set-partition bookkeeping at “O(E + V log V)” and then observes that “we already need O(E log E) = O(E log V) time just to sort the edges”, so the union-find half of the algorithm is not what you pay for; cp-algorithms reaches the same total, “O(M log N + N + M) = O(M log N)”.

Say this before writing a spanning tree

Is the cost I am minimising a sum over the edges I keep, or a path cost from one named node? Sum over kept edges, no start node, “connect everything” → minimum spanning tree. One named source, “shortest” or “fastest to reach” → Dijkstra (lesson 0021). If the graph is directed, a spanning tree is almost certainly the wrong object — this lesson's lemma is stated for undirected graphs.

Bug one: taking the n−1 cheapest edges. Sorting is so clearly the right first move that it is easy to think it is the only move and just keep the first n−1 edges. Measured on 20,000 random connected graphs of 4–7 nodes with weights 1–1000, that set was not even a spanning tree — a cycle somewhere, a node unreached somewhere else — in 8,595 cases (43.0%), and its total was off the optimum in 8,584 (42.9%). The component test is not a refinement of sorting; it is the half of the algorithm that makes the result a tree.

Bug two: handing in Dijkstra's tree. On the same 20,000 graphs, the tree of settling edges from node 0 had a different total from the minimum spanning tree in 11,938 cases — 59.7%. With tie-heavy weights (1–9) it was 13,062, 65.3%. And when every edge weight was made identical, both bugs scored 0 of 20,000: every spanning tree has n−1 edges, so when they all cost the same, every spanning tree is minimum. This is the same shape as lesson 0010's sort-key bugs and lesson 0026's identity bug: invisible exactly on the clean example you would sketch on a whiteboard, wrong on most real inputs.

Checked against a slower, honest reference

min_spanning_tree was compared against brute force — enumerate every subset of n−1 edges, discard the ones that aren't spanning trees, keep the lightest — on 60,000 random connected graphs in three weight regimes (1–1000, 1–9, and all-equal). 0 disagreements on total weight, and the edge set it returned was a spanning tree every time.

On LeetCode 1584's largest shape — 1,000 points, so a complete graph of 499,500 edges — it ran in 0.68 s in plain Python. Worth knowing for the interview conversation: the loop closed the tree after examining only 2,911 edges, 0.6% of them, so the break saves nearly all the union-find work — and none of the sort, which is why the cost stays O(E log E) regardless.

Saying it out loud

"The cost here is a sum over the edges I keep, and no node is
 named as a start - so this is a minimum spanning tree, not a
 shortest-path problem. Dijkstra's tree would optimise trips
 from one node, which isn't what's being paid for.

 Kruskal: sort all edges lightest first, then walk them and
 keep an edge only if its two endpoints are currently in
 different components. Lightest-first order means any edge I
 look at is safe exactly when its ends are in different pieces,
 and the safe-edge lemma says every safe edge is in the answer.

 The component test is union-find, near-constant per edge, so
 sorting dominates: O(E log E). Here that's 1,000 points, a
 complete graph, about 499,500 edges - fine. I stop once I've
 kept n-1 edges, since that's a spanning tree."

Read this next (primary source)
