The Root Knows One Thing

Every earlier lesson's licence was about the whole input — monotonic, sorted, overlapping. A heap's licence is smaller than any of those, and that is the whole point of it: you give up knowing the order of everything, in exchange for never having to pay for it.

A heap answers exactly one question fast: what is the smallest (or largest) thing in here right now? "A priority queue (or heap) supports the following operations: insertion of elements, deletion of the element considered highest priority, and retrieval of the highest priority element, all in O(log N) time." (USACO Guide) It does not answer "what is the second-smallest" or "is 7 in here" without more work. That narrowness is the licence, and it is why a heap is faster than a sorted structure at the one thing it does.

The trade

Python's heapq keeps a list satisfying one rule: "Min-heaps are binary trees for which every parent node has a value less than or equal to any of its children," so "the smallest element is always the root, heap[0]." (Python docs) Nothing is promised about the order of anything else — the second-smallest element could be anywhere in the list. That is a weaker guarantee than a sorted array's, and giving up the extra structure is exactly what makes push and pop O(log n) instead of the O(n) a sorted list would need to stay sorted after every insertion.

Say this before "heap"

A partial order: you know how the root compares to everything else, and nothing about how the rest compare to each other. Every earlier licence in this course was a promise about the whole input in advance. This one is a promise about exactly one element, refreshed after every change — which is why it is the tool for a collection that keeps changing.

The tell: static, or growing one at a time

Same question, two problem statements one word apart. LeetCode 215 hands you the whole array once and asks for the k-th largest element. LeetCode 703 asks for the same number, but the array does not exist yet: values arrive one at a time, and every arrival needs an answer.

# LC 215 — one shot, the array is handed to you complete
import heapq
def kth_largest_static(nums, k):
    return heapq.nlargest(k, nums)[-1]

# LC 703 — the array does not exist yet; it grows one call at a time
class KthLargest:
    def __init__(self, k, nums):
        self.k = k
        self.heap = []
        for v in nums:
            self.add(v)

    def add(self, val):
        heapq.heappush(self.heap, val)
        if len(self.heap) > self.k:
            heapq.heappop(self.heap)
        return self.heap[0]

Nothing about the value being asked for changed. What changed is the shape of the input: one array versus a stream of calls, each expecting an answer before the next arrives. The shape lesson (0002) taught you to read this off the output; this is the same reading applied to when the input itself is finished. A one-shot array can be sorted once and forgotten. A stream cannot be sorted once, because it is not done arriving.

The inversion

The instinct for "k-th largest" is to reach for a max-heap. That instinct is backwards, and seeing why is the actual content of this lesson. A max-heap of everything seen so far tells you the largest value in O(1) — but the k-th largest is buried k−1 pops deep inside it, and popping loses elements you still need for the next query. What you actually want is a min-heap capped at size k, holding only the k largest values seen. Its root is the smallest of those k — which is precisely the k-th largest overall:

self.heap = []          # min-heap, capped at size k
def add(val):
    heapq.heappush(self.heap, val)
    if len(self.heap) > self.k:
        heapq.heappop(self.heap)   # discard the one member that ISN'T top-k
    return self.heap[0]            # smallest-of-the-largest-k == k-th largest

The cap is doing two jobs at once: it keeps the heap small (O(log k) per insertion instead of O(log n)), and it is what makes the root correct — not a performance nicety layered on top. Drop the cap and the root stops meaning "k-th largest" at all.

Measured, not asserted. Delete the three-line cap — push every value, never pop — and the code still runs, still returns heap[0], and still looks like a reasonable heap-based solution. On the very first query of every stream it is correct: the heap happens to hold exactly k elements at that point, same as the capped version. 0% disagreement across 20,000 random streams, first query only.

From the second query on, the uncapped heap keeps growing, and its root drifts toward the running minimum of the whole stream instead of the k-th largest. Disagreement with a brute-force re-sort after every insertion: 99.0% of 80,575 later queries across the same 20,000 streams. The bug is invisible on the one case you'd sanity-check by hand and wrong on almost everything after it.

Why bother

The alternative to any of this is honest and simple: keep a plain list, re-sort it after every insertion, read off index k-1. It is also correct. The only reason not to do it is speed, so the claim should be measured rather than taken on faith:

Measured on CPython 3.12, a stream of 6,000 random insertions, k = 10: the capped min-heap answers every query in 1.7 ms total. Re-sorting the growing list after each insertion and reading index 9 takes 105 ms — about 60× slower, and the gap widens with every additional insertion, because re-sorting pays O(n log n) on a list that is already almost sorted, once per arrival, while the heap pays O(log k) — and k never grows.

Reading it before you write it

Lesson 0001's constraint ladder reads n for a time budget. A heap problem needs one more reading, and it is not about n at all: does the collection keep changing while you're being asked questions about it, or is it handed to you complete? "Priority queues are simpler and faster than sets, so you should use them instead whenever possible" (USACO Guide) — whenever, that is, you only ever need the current extreme, not an arbitrary lookup. The moment a problem also needs "is x still in here" or "what is the median", a heap alone stops being enough, and a sorted structure earns its extra cost back.

Saying it out loud

"This is asking for the k-th largest, and it's asked repeatedly
 as values arrive - so I'm not going to sort on every call, I'll
 keep a heap instead.

 The instinct is 'largest, so max-heap' - that's backwards. I want
 a MIN-heap, capped at size k, holding the k largest values I've
 seen. Its root is the smallest of those k, which is exactly the
 k-th largest overall.

 The cap isn't just for speed - it's what makes the root mean the
 right thing. Without it the root just drifts toward the global
 minimum as more values come in.

 If this were a one-shot array instead of a stream, I'd just sort
 once and index in - no heap needed. The heap earns its cost only
 because the collection keeps changing under me."

The sentence worth having ready is "the cap isn't for speed, it's what makes the root correct" — it is the difference between a heap that happens to run fast and a heap that answers the right question.
