What the Children Return

Almost every tree problem is one recursive function on one node. So the pattern is never the hard part — naming it takes two seconds. The decision that actually decides whether your code is right is what that function returns, and there is one classic way to get it wrong that no hand-drawn test case will catch.

The tree is the recursion. Lesson 0007 built recursion over a number — solve(x) calling solve(x - c). A tree hands you the recursion ready-made: "the structure of a rooted tree is recursive: each node of the tree acts as the root of a subtree that contains the node itself and all nodes that are in the subtrees of its children." (Competitive Programmer's Handbook, ch. 14)

So the shape of the solution is decided before you read the question: def f(node), which asks its children and combines their answers. The state from lesson 0007 is just the node. What is left to decide is the thing this lesson is about — what f hands back.

One tree, three questions

Everything below uses the same 7-node tree, rooted at node 1. Trees in interview problems arrive either as objects with .left/.right, or — in the general case, and in every competitive-programming problem set — as an adjacency list: a map from each node to its neighbours, with no direction marked.

adj = {1: [2, 3], 2: [1, 4, 5], 3: [1, 6],
       4: [2], 5: [2, 7], 6: [3], 7: [5]}

#          1
#        /   \
#       2     3
#      / \     \
#     4   5     6
#          \
#           7
The detail that bites first

An adjacency list has no direction: node 2's neighbours are [1, 4, 5], and 1 is its parent. Recursing into every neighbour walks straight back up and then straight back down, forever. Every tree DFS over an adjacency list therefore carries the node it came from and skips it — "the purpose of the parameter e is to make sure that the search only moves to nodes that have not been visited yet." (CPH, ch. 14) A tree has no cycles, so this one test is all the visited-tracking you need.

Up: return values

First question: how tall is the tree? The height of a node is the number of edges on the longest downward path from it to a leaf. A node cannot answer that until its children have, and then it takes the best of them and adds its own edge:

def height(node, parent):
    best = 0
    for kid in adj[node]:
        if kid != parent:
            best = max(best, 1 + height(kid, node))
    return best

height(1, None)   # 3

Nothing here knows about the tree as a whole. Node 5 knows only that its one child returned 0, so it returns 1. The answer for the whole tree assembles itself out of seven local returns. This is post-order: "recursively visit all children before processing the current node" (USACO Guide), and it is forced here rather than chosen — a node physically cannot compute its height first.

Down: parameters

Second question: how deep is each node below the root? Depth is not built from children; it is handed down from the parent. So it does not travel in a return value at all — it travels as an argument, and the node writes its answer down on the way in:

def depths(node, parent, d):
    depth[node] = d
    for kid in adj[node]:
        if kid != parent:
            depths(kid, node, d + 1)

depths(1, None, 0)

That is pre-order: "process the current node before recursively visiting its children" (USACO Guide). Same walk, same parent guard, same O(n) — only the line where the work happens moved above the loop instead of below it.

The whole lesson in one line

Information flows down through parameters and up through return values. Before writing a tree function, say which one you need. If the answer at a node depends on what is above it, pass it in. If it depends on what is below it, return it. Pre-order and post-order are not two techniques to memorise — they are just where the work line sits relative to the loop, and that is decided by which direction the information came from.

Both at once — and the bug that lives here

Third question: what is the diameter — the longest path between any two nodes? CPH's move is to root the tree and notice that "every path in a rooted tree has a highest point: the highest node that belongs to the path", so it is enough to compute, for each node, the longest path whose highest point is that node. It names two quantities, and the naming is the point:

  • toLeaf(x) — "the maximum length of a path from x to any leaf"
  • maxLength(x) — "the maximum length of a path whose highest point is x"

For our tree, the answer is 5: the path 7 → 5 → 2 → 1 → 3 → 6, whose highest point is the root. At the root, toLeaf of the two children are 2 and 1, so the path through the root is (1 + 2) + (1 + 1) = 5. And here is the trap. The question asks for maxLength. The parent needs toLeaf. Those are different numbers, and the recursion must return one and record the other:

def diameter(root):
    best = 0

    def to_leaf(node, parent):
        nonlocal best
        tops = sorted((1 + to_leaf(kid, node) for kid in adj[node] if kid != parent),
                      reverse=True)
        best = max(best, sum(tops[:2]))    # record: the path THROUGH node
        return max(tops[:1], default=0)    # return: the deepest path FROM node

    to_leaf(root, None)
    return best

tops holds, for each child, the depth of the deepest path from node down through that child. The two largest of them joined at node form the best path with node at the top — that gets recorded in best, and then thrown away. What goes back to the parent is only the single deepest branch, because that is the only thing the parent can extend.

Measured, not asserted. Change the last line to return sum(tops[:2]) — return the number you were asked for instead of the number the parent needs — and everything still runs, still terminates, and is still O(n). On our 7-node tree above it answers 6 instead of 5, which is a path longer than any path the tree even contains. Across 20,000 random trees it disagrees with a brute-force all-pairs BFS on 81.2% of them, always an overestimate.

The reason this ships is in the next two numbers. On path-shaped trees it is wrong 0% of the time, and on star-shaped trees 0% of the time — because with only one child, "the deepest branch" and "the path through me" are the same number. Those are exactly the two trees you sketch on paper to check your work.

The tell you have to read from the constraints

A recursive DFS is the right shape and can still be the wrong code, for a reason that has nothing to do with trees. Python's stack is bounded: "the maximum depth of the Python interpreter stack … This limit prevents infinite recursion from causing an overflow of the C stack and crashing Python." (Python docs) The default is 1000, and a tree with n = 2·105 nodes is allowed to be one long path.

Measured on CPython 3.12: height on a path of 999 nodes returns fine; on 1000 it raises RecursionError. With sys.setrecursionlimit(300_000) the same function handled a path of 200,000 nodes. That fix is standard for judges but not free — the docs warn that "the highest possible limit is platform-dependent … this should be done with care, because a too-high limit can lead to a crash." The alternative is an explicit stack, which is why interviewers ask for the iterative version.

So the bound n ≤ 2·105 on a tree problem carries a second message beyond the time budget from lesson 0001: say out loud that a path-shaped input would blow the default recursion limit, and what you would do about it. It costs one sentence and it is the kind of thing that separates "knows the pattern" from "has shipped this".

Saying it out loud

"It's a tree, so the recursion is already given to me: one
 function on a node, combining what its children hand back.
 The state is just the node.

 First question - which direction does the information move?
 What I'm asked for here depends on the subtree below each node,
 so it comes up in return values, and the work goes after the
 loop. Post-order.

 Second question, and this is the one I actually get wrong -
 is what I return the same as what I'm asked for? Here it isn't.
 The parent can only extend a single downward branch, so that's
 what I return; the answer that turns around at this node gets
 recorded in a running best and then dropped.

 It's an adjacency list, so I pass the parent down and skip it -
 that's all the visited-tracking a tree needs.

 One more thing on the bound: n is 2 times ten to the fifth and
 nothing says the tree is balanced, so a path-shaped input is
 200,000 frames deep against Python's default limit of 1000.
 I'd raise the recursion limit, or go iterative if you'd prefer."

The two sentences worth having ready are "the information comes from below, so it returns" and "what I return isn't what I was asked for". The second one is the Staff+ signal: it says you have met this bug before.
