Counterexample Before Code

Lesson 0010 showed a greedy rule that works (sort by end) and one that does not (sort by start). This lesson is the general test for telling them apart: try to break the rule on a tiny input first, and only if it survives, give the one-sentence exchange argument. Two problems, one that passes the test and one that fails it.

The tell is “obvious best choice, and the constraints forbid trying everything.” Greedy is a candidate whenever one local rule seems to settle each step (largest coin, furthest reach, earliest end). Rule it out the moment you find a small counterexample; fall back to dynamic programming (lesson 0007) when the choice has to be kept open. Constraints such as n ≤ 105 (lesson 0001) are what push you to look for greedy at all.

A greedy rule that fails

The Competitive Programmer’s Handbook, chapter 6, defines the approach: “A greedy algorithm constructs a solution to the problem by always making a choice that looks the best at the moment. A greedy algorithm never takes back its choices.” It warns that “it is often difficult to argue that a greedy algorithm works”, and its first example is the coin problem of lesson 0007 (fewest coins summing to x). Take the largest coin that fits, repeatedly. With euro coins that is correct. For coins {1, 3, 4} and x = 6 it picks 4 + 1 + 1 (three coins) while 3 + 3 (two) is better. The handbook’s verdict: “We can prove that a greedy algorithm does not work by showing a counterexample.”

That is the whole test, and it is cheap: spend a minute on inputs of size 3 to 5 before writing any code. We measured how often it matters. Over 20,000 random coin sets (always including a 1, so every amount is reachable; two to four coins up to 12; x from 1 to 30), largest-coin-first disagreed with the lesson 0007 table on 1,967 (9.8%). On the euro coins it disagreed on 0 of the amounts 1 to 2,000, so the rule is not “greedy never works on coins” but “it works on some coin sets, and you must check which.”

A greedy rule that survives

LeetCode 55, Jump Game: nums[i] is the longest jump allowed from index i; can you get from index 0 to the last index? Two rules sound equally plausible. Rule A: always take the longest jump from where you stand. Rule B: track the furthest index reachable from anywhere you could have been.

Run the counterexample hunt on A. For [2, 2, 0, 0] rule A jumps 0 → 2 and is stuck on a zero, yet 0 → 1 → 3 reaches the end. A is dead in four numbers. (Over 20,000 random arrays of length 1–8 with values 0–4, rule A disagreed with an exhaustive search on 1,178.)

Rule B has no such counterexample, and here is why, in one sentence: every index up to the current reach is itself reachable, so remembering only the maximum loses nothing. That is the exchange argument. Any other plan for where to stand can be swapped for “the furthest” without shrinking the set of indexes you can continue from — the same shape as the handbook’s scheduling proof, “selecting an event that ends later can never yield a better solution.”

def can_jump(nums):
    reach = 0                          # furthest index reachable so far
    for i, x in enumerate(nums):
        if i > reach:                  # a gap: index i cannot be reached
            return False
        reach = max(reach, i + x)
    return True

One pass, O(n) time, O(1) space. It was compared with a memoised exhaustive search on the same 20,000 arrays and disagreed on 0.

Say this before writing the loop

The obvious local rule is furthest reach. Before I trust it I try to break it on small inputs; I could not, and the reason is that everything up to the reach is reachable, so keeping only the maximum discards nothing. If I had found a counterexample I would switch to a table that keeps every state.

The proof is not decoration. A rule can survive your five hand-picked tests and still be wrong, which is why the handbook calls the argument “often difficult”. The counterexample hunt can only rule a rule out; the exchange sentence is what lets you rule it in. If you cannot say the sentence, say so to the interviewer and offer the DP, which is always safe.

Saying it out loud

"Can you reach the last index, n = 10^5. Trying every jump sequence is
 exponential, so I want a local rule. Longest jump from here sounds
 right, but [2, 2, 0, 0] breaks it: it lands on a zero while 0 to 1 to 3
 works. That rule is out.

 Furthest reach survives: every index up to the reach is itself
 reachable, so keeping only the maximum loses nothing. One pass, fail if
 the index passes the reach. O(n) time, O(1) space.

 If I could not state why it holds, I would fall back to a table over
 indexes, which is always correct, at O(n^2) worst case."
