Path Compression Pays for Itself

Lesson 0015 answered “fewest edges” with BFS over a fixed graph, read once. This lesson answers a different question — “are these two nodes connected,” asked over and over, with edges arriving one at a time — where re-running BFS after every edge is the slow way to get the right answer. A disjoint-set forest tracks connectivity directly: two cheap operations, find and union, and one habit — never attach the bigger tree under the smaller one — that keeps both of them nearly O(1).

The tell is repeated or incremental connectivity questions — “are a and b in the same group,” “how many groups are there now,” asked again after every new edge — with no need for the actual path between them. The moment the question becomes “what is the path” or “how many edges,” this tool stops being enough and you want lesson 0015's BFS/DFS over the whole graph instead.

Why re-running lesson 0015 is the slow way

Nothing stops you from answering “are a and b connected” by running BFS from a after every new edge and checking whether it reaches b. It is correct. It is also O(V+E) per question, and if m edges arrive one at a time and you ask after each one, that is O(m·(V+E)) overall — the whole graph, rebuilt from scratch, just to answer one yes/no.

A disjoint-set forest keeps the answer standing instead of recomputing it. Every node points at a parent; two nodes are connected exactly when walking parents from each one reaches the same root:

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))
        self.size = [1] * n

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path compression
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                 # already connected — this edge closes a cycle
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra             # smaller tree hangs under the bigger one
        self.size[ra] += self.size[rb]
        return True

The one habit that makes both operations cheap

find walking parent pointers and union relinking one root under another are each trivial in isolation. What makes the forest fast over many operations is a pair of habits working together: union by size (the smaller tree always hangs under the bigger one, so no tree's height can double without its size at least doubling too) and path compression (every find flattens the pointers it walks, so the next lookup is shorter). The USACO Guide states what the combination buys: with the union-find structure in place, you can “unite vertices and check if two vertices ui and vi are in the same connected component using only O(α(N)) amortised time” — amortised, meaning averaged over the whole run, the same word lesson 0003's window used for the same reason. α is the inverse Ackermann function, which is at most 4 for any N you could ever construct; in practice this is “a handful of pointer hops, however many operations you run.”

Say this before writing a connectivity structure

Am I asking “connected or not” / “how many groups,” repeatedly, as edges arrive — or do I need the actual path or edge count between two nodes? The first is union-find; the second is lesson 0015's BFS/DFS. And when I union two roots, am I attaching the smaller tree under the bigger one, or just picking a side by habit?

The bug that still terminates, and still gets the right answer — slowly. Skip the size check and always attach the second argument's root under the first's, and every find and every union still returns the correct answer. Nothing crashes, nothing disagrees with the correct version. But chain the same n − 1 unions (union(0,1), union(1,2), …) into both versions, n = 2000, then call find on every node once: the union-by-size version does 1,999 total parent-pointer hops across all 2,000 calls — a flat tree, roughly one hop each. Skipping the size check turns the forest into a single 1,999-long chain, and the same 2,000 calls cost 1,999,000 hops — a thousandfold blow-up, from one comparison left out.

Checked against a slower, honest reference

The worked example — LeetCode 684, Redundant Connection: edges of a tree arrive one at a time, plus exactly one extra edge that closes a cycle; return the edge that closes it. union returns False on that exact edge, because its two endpoints already share a root. Checked on 3,000 random trees with one added edge, each one built, shuffled and solved independently, against a second plain-Python union-find written from scratch as the reference implementation: 0 of 3,000 disagreed.
