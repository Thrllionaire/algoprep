Fingerprint, Then Check

Lesson 0004 turned a subarray into a pair of prefix boundaries, so its sum became one subtraction. A rolling hash does the same to a substring: keep a prefix array of fingerprints, and any substring's fingerprint is two lookups. Comparing two substrings then costs O(1) instead of their length — with one catch the lesson is built around.

The tell is equality of many same-length substrings — “find the pattern in the text”, “does any length-L block repeat”. Rule it out when the question is approximate (edit distance, lesson 0020) or many words share prefixes (a trie, lesson 0019): a hash answers “equal?” and nothing else. Constraints like n ≤ 105 (lesson 0001) are what say slicing every window is too slow.

The question

Find every position where a pattern occurs in a text (LeetCode 28 is the single-answer version). The cp-algorithms statement is to “determine if the pattern appears in the text and if it does, enumerate all its occurrences in O(|s| + |t|) time.” The obvious way compares the pattern against each window character by character. On a text of 100,000 as and a pattern of 49,999 as then a b, every window matches all the way to the last character, which is (n − m + 1) · m = 2,500,050,000 comparisons. The hash version below does about 200,000 operations on the same input.

A fingerprint can eliminate, never confirm

A rolling hash maps a string to a number, and the same string always gets the same number. That asymmetry is the whole lesson. Different fingerprints prove the strings are different — a certain no, which is elimination. Equal fingerprints only make the strings candidates: two different strings can share a number. So you fingerprint every window to eliminate nearly all of them in O(1) each, then compare real characters on the survivors.

The fingerprint is a polynomial: read the string as digits in base B, modulo a large M. Following lesson 0004, store a prefix array H where H[i] is the fingerprint of the first i characters. Then the fingerprint of text[i:j] is H[j] − H[i] · Bj−i. The multiply is the new part: unlike a sum, the first i characters sit j−i digit positions higher inside H[j], so they must be shifted before they can be subtracted away. (cp-algorithms writes the same identity with powers running the other way: “hash(s[i…j]) · pi = hash(s[0…j]) − hash(s[0…i−1]) mod m”.)

import random
M = (1 << 61) - 1                          # large prime modulus

def find_all(text, pat):
    n, m = len(text), len(pat)
    if m == 0 or m > n:
        return []
    B = random.randrange(256, M - 1)         # random base, chosen per run
    H, P = [0] * (n + 1), [1] * (n + 1)      # prefix fingerprints, powers of B
    for i, ch in enumerate(text):
        H[i + 1] = (H[i] * B + ord(ch)) % M
        P[i + 1] = P[i] * B % M
    target = 0
    for ch in pat:
        target = (target * B + ord(ch)) % M
    hits = []
    for i in range(n - m + 1):
        h = (H[i + m] - H[i] * P[m]) % M     # fingerprint of text[i:i+m]
        if h == target and text[i:i + m] == pat:   # candidate, then confirm
            hits.append(i)
    return hits

Cost is O(n + m) for the fingerprints plus O(m) for each candidate you confirm. With almost no false candidates that is O(n + m) overall — but only on inputs where hits are rare. If every window truly matches (text and pattern all a), each of the n − m + 1 hits costs a full O(m) confirmation, so confirming every hit brings back O(nm). When the question is only “does it occur at all?”, stopping at the first confirmed hit avoids that.

Say this before writing the loop

Comparing windows by slicing costs the window length each. I'll store prefix fingerprints so any window's fingerprint is two lookups. Different fingerprints are a certain no; equal ones are only candidates, so I confirm those against the real characters. Random base, 61-bit prime modulus.

Three ways to get it wrong, measured on 20,000 random small cases (text length 1–14, pattern length 1–5, alphabets of 2–4 letters) against a brute-force search. (1) A fingerprint that is the sum of character codes, with no confirmation, disagrees on 6,498 (32.5%): every anagram of the pattern collides. (2) The polynomial hash with a tiny modulus (7) and no confirmation disagrees on 5,078 (25.4%). (3) The same tiny modulus with the confirmation step disagrees on 0 — confirmation is what keeps the answer exact, and the 61-bit version above also scored 0 with and without it. The modulus therefore decides how fast you are, confirmation decides whether you are right.

Why the modulus and base are not decoration

cp-algorithms puts the chance two random strings collide at “≈ 1/m”, and warns that with 106 strings compared against each other “the probability of at least one collision happening is already ≈ 1”. It also says m = 264 “is not recommended”, because a colliding pair can be generated. We checked the strongest form: the Thue–Morse string of length 2,048 and its bitwise complement collide mod 264 for every odd base tried (963 of 963 in a sample of 2,000 random bases), and for no even base (0 of 1,037); mod 261−1, 0 of 1,000 random bases collided. A fixed, well-known base and modulus is the same weakness from the other side: someone can choose input against it, which is why the code draws B at random.
