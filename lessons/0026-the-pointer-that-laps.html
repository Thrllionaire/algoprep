The Pointer That Laps

A singly linked list gives you one thing a plain array doesn't: you cannot look backward, and you may not even know how long it is. “Has it looped back on itself?” still needs an answer, and the trick is two pointers walking the same direction at different speeds — so a faster one that is going in circles eventually runs into the slower one from behind.

The tell is a singly linked list, a question about a cycle or the middle node, and a follow-up asking for O(1) extra space. LeetCode 141, Linked List Cycle: does the list loop back on itself? LeetCode 142, Linked List Cycle II: if so, which node does the loop start at? Close cousins: find the middle node in one pass; detect a cycle in a sequence defined by repeatedly applying a function (Floyd's name for this trick is cycle detection, not just a linked-list party piece).

The visited set works — and costs what lesson 0015 already charged

You already own a tool for “has this node been reached before”: lesson 0015's visited set, which a graph needs because more than one path can reach the same node. A singly linked list is a graph where every node has exactly one outgoing edge, so walking it and recording every node's identity in a set works identically — the moment you revisit something already in the set, there's a cycle.

It also costs O(n) extra memory, one entry per node visited, and the follow-up on both LeetCode problems is explicit: solve it in O(1) extra space. That single constraint is what rules the visited set out and makes this lesson's trick worth having — not a faster asymptotic time, a cheaper space budget, for the specific case where the graph is a single thread rather than a tangle.

Two speeds, one loop

Walk two pointers from the head: slow one step at a time, fast two steps at a time. If the list has no cycle, fast reaches the end first and the loop stops. If it does have a cycle, fast enters the cycle before slow does and then starts lapping it — every step inside the cycle, fast gains one position on slow, so within at most one full lap it must land on the exact node slow is standing on. cp-algorithms states the setup plainly: “slow will move one step at a time. fast will move two steps at a time… check if at any point they point to the same node before any one (or both) reach null.”

def has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:          # same node, not same value - see the caveat
            return True
    return False

Finding where the cycle starts is a second phase, run after the meeting point is found. Reset one pointer to the head, leave the other at the meeting point, then move both one step at a time; where they meet the second time is the cycle's entry node. The source states the move and its payoff together: “Reset the slow pointer to the head of the linked list. Move both pointers one step at a time. The point they will meet at will be the starting point of the cycle” — the distance from the head to the entry turns out to equal the distance from the meeting point back around to the entry, which is exactly what moving both at the same speed from those two starting points discovers.

def cycle_start(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:
            slow = head                     # the reset - see the caveat
            while slow is not fast:
                slow = slow.next
                fast = fast.next
            return slow
    return None
Say this before writing fast and slow pointers

Can I only walk forward, one link at a time, with no index and maybe no known length — and does the question ask about a cycle, a loop-back, or a middle position? If the problem allows O(n) space, a visited set (lesson 0015's tool) answers the same question with less to prove. Fast/slow earns its place only when O(1) space is required or explicitly rewarded.

Bug one: comparing values, not nodes. slow is fast checks identity; swap it for slow.val == fast.val and the code still runs and still looks right, but on lists with repeated values it declares a cycle that was never there — two different positions can simply hold equal numbers. Measured on 20,000 random acyclic lists with values drawn from 0–4 (heavy repetition), the value-equality version falsely reported a cycle on 14,110 — 70.6%. On the same lists with values drawn from 0–999,999 (collisions now rare), it falsely reported 0 of 20,000 — the bug is invisible exactly when test data happens to use distinct numbers.

Bug two: skipping the reset. If the second phase moves both pointers one step at a time from the meeting point without resetting one to the head first, the two pointers are already standing on the same node, so the “move until they meet” loop exits immediately and simply returns the meeting point — which is almost never the cycle's actual entry. Measured on 20,000 random cyclic lists, the no-reset version returned the wrong node on 15,870 — 79.4% of the time.

What O(1) space actually buys, measured

On a 100,000-node list (half tail, half cycle), the visited-set approach's peak traced memory was 8,808,248 bytes for the set of node identities; has_cycle's peak traced memory was effectively 0 bytes — two pointer variables, however long the list. Both answer the same question; only one of them is paying rent per node.

Checked against a slower, honest reference

has_cycle and cycle_start were run against the visited-set reference on 20,000 random lists, mixing acyclic lists and cyclic ones of random tail and cycle length. 0 of 20,000 disagreed on either question.

Saying it out loud

"Singly linked list, question about a cycle, O(1) extra space -
 a visited set would answer it but costs O(n), so that's out.

 Two pointers from the head: slow moves one step, fast moves two.
 If there's no cycle, fast hits null first. If there is one, fast
 enters it first and then laps slow from behind - the gap closes
 by one node every turn, so they land on the same node within one
 lap. I compare node identity, not value, since values can repeat.

 If I need the cycle's start, not just whether one exists: after
 they meet, reset one pointer to the head, then move both one step
 at a time. Where they meet the second time is the entry."
