Keep With Probability One Over i

Every lesson so far assumed you could look at the input again. This one cannot: items arrive once, you do not know how many are coming, and you must be able to stop at any moment holding a fair random pick. The whole algorithm is one line — the ith item replaces your pick with probability 1/i — and the interesting part is why that one line is fair.

The tell is “random, uniform, one pass, length unknown.” Pick a random node from a linked list you cannot index; pick a random index of a value from an array too big to hold; sample from a feed. If you may read the input twice, or store it, this lesson is not needed — so rule those out first.

The question

Return a uniformly random element of a stream, where you see each element once and do not learn the length until the stream ends. This is the shape of LeetCode 382, Linked List Random Node, and of LeetCode 398, Random Pick Index (pick a random index among those holding a target value). “Uniform” means each of the n items is the answer with probability exactly 1/n.

Rule out the obvious answers first

Two answers come to mind, and each breaks on one word in the question.

Why the usual ways of picking at random do not fit a stream
ApproachWhat it needsWhy a stream rules it out
Store everything, random.choiceAll n items in memoryThe stream may not fit
Count first, then pick index and re-readTwo passesA stream can be read once

The measured cost of the first row: pushing 1,000,000 items through a generator, storing them all and calling random.choice peaked at about 40 MB; the algorithm below, on the same stream, peaked at about 464 bytes (CPython 3.12, tracemalloc). What is left is an answer that keeps one item and a counter.

One line, and why it is fair

import random

def sample_one(stream):
    chosen, seen = None, 0
    for x in stream:
        seen += 1
        if random.randrange(seen) == 0:      # probability 1/seen
            chosen = x
    return chosen

The first item is kept for sure (randrange(1) is always 0). The second replaces it half the time, the third a third of the time, and so on. It is not obvious this gives every item the same chance — the early items get more turns at being replaced, yet start with a much better chance of being the pick. The proof is the lesson’s payload, and it is one line of multiplication. Item i ends up as the answer when it is chosen at step i and then survives every later step i+1 … n:

P(item i is the answer) = 1/i  ×  (i/(i+1))  ×  ((i+1)/(i+2))  ×  …  ×  ((n-1)/n)  =  1/n

Each survive factor is 1 minus the replace probability: at step j the replace probability is 1/j, so survival is (j−1)/j. The numerators and denominators cancel in a chain, leaving 1/n for every i. Nothing in the calculation mentions n until the last factor — that is exactly why you do not need to know the length in advance.

Say this before writing a streaming sample

What is the state — what must I carry for the future to be fair? (Here: the current pick, and how many items I have seen.) If two histories end with the same pick and the same count, is the future identical? And what is the probability that item i is still the pick at the end — does the product telescope to 1/n?

Keeping k instead of one

The same idea with a reservoir of k slots. The Stanford CS168 notes (Roughgarden and Valiant, attributing the algorithm to Vitter) state it as: “Put the first k elements of the stream into a reservoir … for i ≥ k+1, with probability k/i replace a random entry of R with xi.” In code, one draw does both jobs:

def sample_k(stream, k):
    reservoir = []
    for seen, x in enumerate(stream, start=1):
        if seen <= k:
            reservoir.append(x)
        else:
            j = random.randrange(seen)       # uniform in 0..seen-1
            if j < k:                        # probability k/seen
                reservoir[j] = x             # and j is the slot to overwrite
    return reservoir

j < k happens with probability k/seen, and when it does, j is already a uniformly random slot — so one draw supplies both the “whether” and the “where”. The notes’ proof is induction: an item present after step t survives step t+1 with probability (1 − k/(t+1)·(1/k)) = t/(t+1), which turns k/t into k/(t+1). Setting k = 1 gives exactly the function above.

Tested exactly, not just sampled

Randomised code is easy to believe in and hard to check, because a wrong version still returns plausible items. So both functions above were tested exhaustively: random.randrange was replaced with a script that feeds in every possible sequence of draws, and the final answer was tallied. For every n from 1 to 7, sample_one returned each item the same number of times, and for every n up to 7 and every k up to n, sample_k returned every one of the C(n, k) subsets the same number of times. That is not a statistical claim; it is an enumeration of every outcome.

The bug that passes the sample. A tempting simplification: “flip a fair coin at each item and keep it on heads.” It returns a real element of the stream every time, and on a single run nothing looks wrong. Over 200,000 runs on a stream of five items, the correct version picked each position about 20% of the time (0.200, 0.200, 0.199, 0.199, 0.201). The coin version picked them 3.0%, 6.2%, 12.6%, 24.8%, 50.2% of the time — the last item wins half the time, because only it never has to survive a later flip. The fix is not “more randomness”; it is that the replace probability must shrink as 1/i to compensate for the early items having more chances to be overwritten.

Saying it out loud

"Uniform random item, one pass, length unknown - so I can't store
 the stream and I can't count first. I keep one pick and a count.
 When item i arrives, it replaces the pick with probability 1 over i:
 randrange(i) == 0. The first item always sticks.

 Why that's fair: item i ends as the answer if it was chosen at
 step i, probability 1/i, and then survives every later step j,
 probability (j-1)/j. That product telescopes to 1/n for every i,
 and n never appears until the last factor, which is why I didn't
 need to know it.

 State is the pick and the count. For k items, same thing: keep the
 first k, then for item i draw j in 0..i-1 and, if j < k, overwrite
 slot j - that's k/i and a uniform slot in one draw."
