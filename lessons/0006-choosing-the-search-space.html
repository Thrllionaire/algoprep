Choosing the Search Space

Every lesson so far handed you a search space — an array, a set of boundaries, a range of indices. This one is different: there is no array to search at all. You build the search space out of thin air, from the range of numbers the answer could possibly be.

Not a minimal pair this time — a contrast between two problems that don't look alike at all, on purpose.

LeetCode 704, Binary Search. Given a sorted array of integers and a target, return the index of target, or −1.
LeetCode 875, Koko Eating Bananas. Given piles of bananas and h hours, find the minimum integer eating speed so Koko finishes all piles within h hours.

704 has an array. 875 doesn't have anything to binary search over — no array, no sorted structure, nothing you were handed. And yet the standard solution to 875 is also called binary search. That's only true because binary search was never really about arrays.

What binary search actually needs

In 704, the search space is the array's indices, and the thing that licenses halving it is that the array is sorted: compare the middle element to the target, and one whole half is provably eliminated. Nothing about that argument mentions arrays specifically — it only needs a range of candidates and a question you can ask of the midpoint that eliminates half of them.

USACO Guide — Binary Search states the generalisation plainly: "Similarly to how binary search on an array only works on a sorted array, binary search on the answer only works if the answer function is monotonic." Sortedness and monotonicity are the same requirement, restated for two different kinds of search space.

In 875 there is no array of candidate speeds — you construct one: every integer from 1 to max(piles) is a candidate eating speed. Feed a candidate speed into a feasibility check (ours) — a function that answers "does this candidate work?" — and the same halving argument applies, as long as the check is monotonic in the candidate: a faster speed can only need the same or fewer hours, never more. That's the whole trick. You're not searching data any more; you're searching the space of possible answers.

The reframe

Binary search needs a search space and a monotonic predicate over it. An array sorted by value is one way to get both. A range of candidate answers plus a feasibility check is another — and it's available even when nothing in the problem is sorted, or an array, at all.

Building the search space for Koko

Lower bound: speed 1 is always a legal candidate to try, even if it's hopeless. Upper bound: speed max(piles) always finishes in exactly len(piles) hours — one pile per hour — so it's always feasible. That's the whole space: [1, max(piles)], guaranteed to contain the answer at both ends.

The feasibility check is one line: total hours needed at a given speed is the sum, over every pile, of that pile divided by the speed and rounded up.

def hours_needed(piles, speed):
    return sum((p + speed - 1) // speed for p in piles)

hours_needed is non-increasing in speed — raising the speed never raises the hours for any single pile, so it never raises the total. That monotonicity is the entire licence for what follows.

The invariant

At the top of the loop, lo is the smallest candidate not yet ruled out, and every speed below lo has been proven too slow. hi is a speed already proven fast enough. The answer is somewhere in [lo, hi], and it always is — the loop only ever discards values on the side that's been proven wrong.

def min_eating_speed(piles, h):
    lo, hi = 1, max(piles)
    while lo < hi:
        mid = (lo + hi) // 2
        if hours_needed(piles, mid) <= h:
            hi = mid          # mid works: the answer is mid or slower... i.e. <= mid
        else:
            lo = mid + 1      # mid is too slow: rule it out entirely
    return lo

This is the mirror image of lesson 0003's shrink loop: there, left only ever moved forward, retiring positions for good. Here, lo and hi only ever move toward each other, retiring whole halves of the candidate range for good. Same amortised bookkeeping, same reason it's fast: O(log(max(piles))) iterations, each doing O(n) work inside hours_needed, for O(n log(max pile))) total — nowhere near the O(max(piles) × n) of trying every speed one at a time.

Property-tested against the obvious brute force — try every speed from 1 upward and return the first that's feasible — on 30,000 random small pile sets: 0 disagreements. The brute force is the spec; the binary search is just the fast way to evaluate it, which is exactly why the two must never diverge.

The licence check, and what happens when it fails

Monotonicity is not a formality here — it's the one fact doing all the work, same as sorted did for lesson 0005's inward walk and at most did for lesson 0003's window. If the feasibility check can flip from true back to false as the candidate grows, binary search doesn't degrade gracefully. It returns a confident, wrong answer, because the halving step throws away a half that might still contain the truth.

Concrete counterexample: is x reachable as a subset sum of [2, 3]?

True, false, true, false, true — there is no single point where it flips once and stays flipped, so there is no boundary for a binary search to converge on. Run the standard "leftmost true" template against this predicate anyway, on random small integer lists, and it disagrees with a linear scan on 69.0% of 30,000 trials — worse than a coin flip, because the template's halving step is actively working against you rather than just failing to help.

The tell to say out loud before reaching for this tool: "if a candidate works, does every candidate on the feasible side of it also work?" If you can't answer yes with a one-sentence proof — the way "faster speed never needs more hours" is one sentence — you don't have a licence yet, no matter how much the problem smells like an optimisation.

Practice

Commit to an answer, and the one-sentence monotonicity proof, before revealing the options.

Saying it out loud

"This is asking me to minimize/maximize some integer quantity under a
 constraint, and there's a natural range the answer must live in.

 Before reaching for binary search, I need one sentence: if a candidate
 in that range works, does every candidate on the feasible side of it
 also work? For Koko, faster speed never needs more hours - that's the
 proof, and it's the whole licence.

 Given that, I don't need the piles sorted or anything else about the
 array - I binary search the range [1, max(piles)] directly, checking
 feasibility at each midpoint and halving the range each time.

 O(n) per check, O(log(max pile)) checks - log of the range, not the
 array - and it's provably correct because the halving step only ever
 discards a side I've just shown can't contain the answer."

The sentence worth saying to an interviewer is the same shape as lesson 0005's: not "I'll binary search this" but "the feasibility check is monotonic because …, so I can binary search the answer instead of trying every candidate." Naming the proof, not just the tool, is what separates recognising the shape from actually establishing you're allowed to use it.
