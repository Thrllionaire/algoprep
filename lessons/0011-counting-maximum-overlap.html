Counting Maximum Overlap

How many meetings are happening at once, at the busiest instant? The whole schedule is handed to you up front, exactly like lesson 0010's intervals — but this time the quantity you're tracking really does rise and fall as you sweep through it, which is exactly what lesson 0009's heap is for. Two correct solutions, from two different lessons, meet on the same problem.

Static input, dynamic count. Lesson 0009's tell for a heap was whether the collection kept changing while you were being asked about it — a growing stream. Lesson 0010's tell for skipping a heap was that the whole list of intervals was handed over before any work started. Both are still true here: nothing new arrives mid-algorithm. What's new is that the question — how many meetings are open right now — is itself a moving target as you walk through time, even though the input describing it never moves. A heap can track that. So can a running counter, if you're willing to give up knowing which meeting is open and keep only how many.

The question

Given a list of meeting intervals [start, end), what is the fewest rooms you need so that no two meetings sharing a room ever overlap? That is exactly the same number as: at the single busiest instant, how many meetings are open at once? Two meetings that touch — one ending the exact instant another begins — do not count as overlapping; the room is free again the moment it's vacated. This is the named interview problem LeetCode 253, Meeting Rooms II (locked behind LeetCode premium); the identical problem is free to practice as CSES 1164, Room Allocation.

Say this before touching an overlap-counting problem

The whole list is handed to me now — so no live structure is forced on me the way lesson 0009's stream forced one. But the thing I'm counting still changes as I sweep through time, so I get to choose between a heap that tracks which rooms are open, or a plain counter that only tracks how many are.

Solution one: a heap of end times

This is lesson 0009's licence, reapplied. Sort meetings by start time, then walk through them one at a time, keeping a min-heap of the end times of every room currently allocated. Before opening a new meeting, check the room ending soonest: if it has already ended, reuse it — pop it, push the new end time, room count unchanged. If it hasn't, no room is free; push a new end time, room count grows by one.

import heapq

def min_meeting_rooms_heap(intervals):
    if not intervals:
        return 0
    intervals = sorted(intervals)          # sort by start
    heap = []                              # end times of allocated rooms
    for start, end in intervals:
        if heap and heap[0] <= start:      # earliest-ending room is free
            heapq.heappop(heap)
        heapq.heappush(heap, end)
    return len(heap)

Checking only heap[0] is enough to know whether any room is free — not just the earliest-ending one. This is lesson 0009's partial order doing real work: a min-heap only guarantees one fact, that the root is no greater than anything else in it. So if the root's end time hasn't passed yet, nothing else's has either, and there is no point checking further.

Solution two: a running counter over events

Lesson 0010's skeleton — sort once, sweep once — still applies, but this time the sweep doesn't compare each interval to its predecessor; it turns every interval into two point events and lets a single counter do the work. Each start becomes an arrival (+1), each end becomes a departure (−1). Sort all of those events by time and sweep left to right, tracking a running total and its maximum.

def min_meeting_rooms_sweep(intervals):
    events = []
    for start, end in intervals:
        events.append((start, 1))
        events.append((end, -1))
    events.sort(key=lambda e: (e[0], e[1]))   # -1 sorts before +1 at equal time
    rooms = best = 0
    for _time, delta in events:
        rooms += delta
        best = max(best, rooms)
    return best

Nothing here ever asks which meeting is open — only how many. That's the trade: the heap solution could tell you which physical room a meeting is assigned to (it's the one whose end time you just popped and replaced); the sweep only ever answers the count. It's the same existence/count/object distinction from lesson 0002's return type axis, this time separating two solutions to one problem rather than two problems.

The one place this needs a tie-break — and it's the whole bug

Lesson 0010 sorted intervals by a single field and never needed a second one, because ties between two full intervals never had to be broken — the comparison happened after sorting, inside the loop. Here, sorting produces a flat list of point events, and two events can land on the exact same time: one meeting's end and another's start. Get the tie-break wrong and a meeting ending at 10 and one starting at 10 read as briefly overlapping, when they should read as back-to-back.

# WRONG: arrivals sorted before departures on a tie
events.sort(key=lambda e: (e[0], -e[1]))

Worked example. [(0, 10), (10, 20)] — one meeting ends exactly as the next begins. The correct sweep returns 1 room: they never overlap. Sort arrivals before departures on the tie instead, and it returns 2: the meeting starting at 10 is counted as open before the one ending at 10 is counted as closed. Quantified over 20,000 random small interval sets, that wrong tie-break disagrees with a brute-force per-instant count on 36.0% of trials — and on 0% of trials built with no touching endpoints at all, which is exactly the kind of input you'd sketch by hand to sanity-check the code and never catch the bug. The USACO Guide states the rule directly: "All events are sorted by time; if two events coincide, departures are processed before arrivals."

 Same answer, same complexity — the heap pays for a stronger guarantee (room identity) with nothing extra, because comparing heap[0] to start already resolves a tie correctly (a room ending exactly at start counts as free). The sweep is leaner but has to state the tie-break out loud, because a flat list of events has no structure protecting it the way a heap does.

Both were property-tested against a brute-force per-instant count on 20,000 random small interval sets: 0 disagreements for the heap, 0 disagreements for the correctly tie-broken sweep. Logged in Resources.

Saying it out loud

"Full schedule, handed to me up front - so no live structure is forced
 on me. But the number of open meetings still rises and falls as I
 sweep through it, so I've got two honest options.

 A heap of end times, reusing 0009's trick: sort by start, and before
 opening a room check whether the soonest-ending one is already free -
 checking just the root is enough, since nothing else can be free if
 it isn't.

 Or a flat sweep, reusing 0010's skeleton: turn every interval into an
 arrival and a departure event, sort, and walk it with a running
 counter. Leaner, but it gives up knowing which meeting is which - and
 it needs a tie-break I didn't need before: departures before arrivals
 at the same instant, or two meetings that just touch get counted as
 overlapping."

The sentence worth having ready is "what's actually changing here - the input, or just the count" — it's what separates this lesson's problem from both 0009's and 0010's, even though the input shape looks like 0010's and the tool looks like 0009's.
