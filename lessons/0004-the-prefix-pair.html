The Prefix Pair

Lesson 0003 ended by telling you a window is illegal the moment values go negative. This is what takes over — and the move is to stop thinking about subarrays.

Here are two problems from the same problem set. Read them slowly; exactly one word differs.

CSES 1660. Given an array of n positive integers, your task is to count the number of subarrays having sum x.
CSES 1661. Given an array of n integers, your task is to count the number of subarrays having sum x.

The word is positive, and dropping it changes the technique completely. That is the whole lesson. By the end you will have a second contiguous tool, and — more usefully — a reframe that makes a large class of problems collapse into the same shape.

Why the window dies here

Run the triage you already have. Both problems say 1 ≤ n ≤ 2·105, which is an O(n) or O(n log n) budget. Both ask about subarrays, so the shape is contiguous and there are n(n+1)/2 candidates — about 2·1010 of them. Enumeration is out. Both ask for a count.

For 1660 that is enough: values are positive, so the sum only rises as the window grows, the predicate is monotonic, and a window is licensed. For 1661 the licence check fails at the first question. Removing an element can raise the sum, so shrinking repairs nothing.

How badly? Running the two-pointer count against brute force on 30,000 random small arrays: on all-positive inputs it disagreed 0 times. On mixed-sign inputs it disagreed on 40.1% of them. This is not a corner case you might get away with — it is wrong on two inputs in five.

So we need a tool whose correctness does not depend on monotonicity at all.

The identity, and the indexing that kills the off-by-one

Build an array p where p[k] is the sum of the first k elements. Note what that means at the ends: p[0] = 0 (the sum of no elements) and p[n] is the total. So p has n + 1 entries, not n.

arr =      2    2   -1   -1   -2    1   -2
p   =  0    2    4    3    2    0    1   -1
       ↑                                  ↑
     p[0]                               p[7]

Then, for any slice:

The only formula in this lesson

sum(arr[l..r]) = p[r+1] − p[l]

The USACO Guide writes this as prefix[R] − prefix[L−1] because it 1-indexes the array. Same identity. The n+1-entry, p[0] = 0 convention is the one that survives contact with Python's 0-indexing, and it is worth adopting once and never rethinking: every off-by-one in this pattern comes from improvising it at the whiteboard.

Precomputing p is one O(n) pass, after which "by precomputing cumulative sums in O(N) time, subsequent queries can be computed in O(1) time" (USACO Guide — Introduction to Prefix Sums). Nothing in that sentence mentions the sign of anything. The identity is arithmetic, and arithmetic has no licence check.

The reframe: a subarray is a pair of boundaries

This is the part worth keeping. Stop picturing a subarray as a run of elements and start picturing it as the two boundaries it sits between. There are n + 1 boundaries, and choosing any two of them, i < j, names exactly one subarray: arr[i..j-1], whose sum is p[j] − p[i].

The correspondence is exact, which you can check against lesson 0002's candidate count: choosing 2 boundaries from n + 1 is (n+1)n/2, which is the same n(n+1)/2 subarrays it told you to expect.

The reframe, in one line

Every question about a subarray is a question about two prefix values. The shape stops being a contiguous run and becomes a pair.

That matters because you already know what to do with pairs, and it is nothing like what you do with runs:

What the pair must satisfyMachineryCost
Differ by an exact amount Hash map of values seen so far O(n)
Differ by as much as possible Running minimum of values seen so far O(n)
Differ by at least / at most some amount Sorted structure or monotonic deque O(n log n)
The second row is Kadane's algorithm, arrived at without being told it was Kadane's algorithm: the best subarray ending at j is p[j] minus the smallest prefix before it. The third is the one to name and then back away from in an interview unless it is asked for.

The complement lookup

Take 1661. "Count subarrays summing to x" becomes "count pairs i < j with p[j] − p[i] = x". Rearrange for the thing you do not know yet:

p[i] = p[j] - x

Now sweep j left to right. At each step you have one concrete number to look up, and the answer is "at each index i, we can count the number of prefixes with sum equal to prefixSum[i]−x" (USACO Guide, CSES Subarray Sums II). A hash map from prefix value to how many times it has occurred answers that in O(1).

from collections import Counter

def count_sum_x(nums, x):
    seen = Counter({0: 1})        # boundary 0 exists before the sweep starts
    run = total = 0
    for v in nums:
        run += v                  # run is now p[j]
        total += seen[run - x]    # count BEFORE inserting
        seen[run] += 1
    return total

Five lines, and two of them are the entire bug surface:

  • Counter({0: 1}). Boundary 0 is a real boundary, not a special case — it is the left end of every subarray that starts at index 0. Forget the seed and you miss exactly those, which is why the symptom is "my answer is a bit too low" rather than a crash.
  • Count before inserting. Insert p[j] first and then look up p[j] − x, and when x = 0 the boundary pairs with itself — counting the empty subarray once per position. Silent, and only on one value of x.
Counter rather than defaultdict(int) on purpose: indexing a missing key on a defaultdict inserts it, so the lookup line would quietly grow the map with zero entries. Correct either way, but Counter returns 0 without writing.

Trace it, don't read it

Same array as above, hunting subarrays that sum to x = −1. Each turn the sweep takes in one more element; your job is to click every earlier boundary that closes a qualifying subarray. Do the subtraction before you look at the tape.

 The asymmetry in the last row is why, when both are available, reaching for the prefix map first is the safer habit — and why saying so out loud is the better interview move.

A correction to lesson 0003, worth making precise. That lesson said "exactly k" defeats a window, because the valid starts form a band rather than one unbroken run. CSES 1660 asks for exactly x with a window and works fine — so which is it?

Both, and the difference is strictness. With strictly positive values the sum is strictly decreasing as left advances, so at most one start can hit x exactly: the band is one cell wide, and a single left can sit on it. Distinct-character counts plateau — several consecutive starts give the same count — so that band is genuinely wide and one pointer cannot mark it. The rule is not "exactly is forbidden"; it is "a band wider than one needs two pointers, and you only have one."

The key does not have to be the sum

This is where the reframe pays for itself. The sweep never cared that the running value was a sum. It cared that the property you want is a difference of two boundary values. Change what you accumulate and the same nine lines answer a different question:

Question about a subarrayAccumulatePartner to look up
Sums to exactly xRunning sump[j] − x
Sum divisible by kRunning sum, mod kp[j]
Equally many 0s and 1sRunning (#1 − #0)p[j]
Every letter appears an even number of times26-bit parity mask, XORedp[j]
 Three of the four look up p[j] itself.

That repetition is not a coincidence, and spotting it is the actual skill. "Divisible by k", "equal counts" and "all even" are the same sentence in three costumes: the difference between the two boundaries is zero. So the partner you are hunting is whatever you are standing on, and the question becomes "have I been in this state before?"

def count_divisible_by_k(nums, k):
    seen = Counter({0: 1})
    run = total = 0
    for v in nums:
        run = (run + v) % k       # the only changed line
        total += seen[run]        # ...and x is 0, so the partner is run itself
        seen[run] += 1
    return total
Every Python snippet on this page was checked against brute force on 30,000 random arrays before publication, mixed-sign included, with zero disagreements. The trace above was generated by replaying count_sum_x and asserting each turn, not written by hand.

Saying it out loud

The triage sentence now has a fork in it. Notice that the licence check is still what decides, and that the reframe gets stated explicitly rather than assumed:

"n is 2e5, so I want O(n). It's a contiguous shape asking for a
 count, and there are about n²/2 subarrays, so I'm not enumerating.

 Values can be negative, so a window isn't licensed — removing an
 element can raise the sum, and then the shrink step repairs nothing.

 So I'll stop thinking about subarrays and think about boundaries.
 There are n+1 prefix boundaries, a subarray is a pair of them, and
 its sum is their difference. I want pairs differing by x, so as I
 sweep j I ask how many earlier boundaries hold p[j] - x. A hash map
 answers that in O(1), seeded with {0: 1} because boundary zero is
 real, and I count before inserting so nothing pairs with itself.

 O(n) time, O(n) space, and it doesn't care about signs."

The sentence that earns the Staff+ marks is the third paragraph, not the fifth. Anyone can recite a prefix-sum template; saying why the previous tool is disqualified and then naming the substitution is trade-off analysis, and it is checkable by the interviewer in real time.

Where this fails. The prefix pair handles exact differences in O(n). It does not give you "at most" or "at least" for free: longest subarray with sum at most k with negatives present needs a sorted structure or a monotonic deque over the prefix array, which is O(n log n) and a different lesson. Prefix sums also assume the array is static — if values change between queries you want a Fenwick or segment tree — and they need an invertible operation, so sum and XOR are fine while min and max are not.
