Prune Before You Recurse

Lesson 0012 counted every subset with an integer. That works when each choice is independent. When a choice can make the rest impossible — two queens on one diagonal — you want to stop the moment that happens, not after all the choices are made. That is backtracking: build the answer one decision at a time, and abandon a partial answer as soon as it is dead.

The tell is a validity rule between choices. “Count all arrangements such that no two …” with a small board or a small n. The answer is an order or placement (lesson 0002), the bound is tiny (lesson 0001), and the conflicts are checkable one choice at a time.

The question

Place eight queens on a chessboard so that no two share a row, column or diagonal; some squares are reserved and cannot hold a queen. Count the valid placements. This is CSES 1624, Chessboard and Queens, and LeetCode’s N-Queens is the same idea. The board is 8×8, so the bound is tiny and exponential is allowed — the only question is how exponential.

The USACO Guide makes the first cut for you: choosing 8 of 64 squares is over four billion placements, but two queens can never share a column, so place exactly one per column and only the row varies. That is a permutation of 8 rows — 8! = 40,320 candidates. Already affordable. Backtracking goes further.

Choose, explore, undo

The Guide’s definition: “A backtracking algorithm begins with an empty solution and extends the solution step by step. The search recursively goes through all different ways how a solution can be constructed.” In code, that is three lines around a recursive call, plus a check before them:

def queens(board):
    n = len(board)
    rows, d1, d2 = set(), set(), set()     # the state: what is already taken
    count = 0

    def go(col):
        nonlocal count
        if col == n:                       # every column filled: one valid placement
            count += 1
            return
        for r in range(n):
            if board[r][col] == '*' or r in rows or r + col in d1 or r - col in d2:
                continue                   # PRUNE: this choice is already dead
            rows.add(r); d1.add(r + col); d2.add(r - col)      # choose
            go(col + 1)                                        # explore
            rows.remove(r); d1.remove(r + col); d2.remove(r - col)   # undo

    go(0)
    return count

Two details do the work. First, r + col is constant along one diagonal and r - col along the other, which is the Guide’s representation (sums and differences of coordinates), so “is this diagonal taken” is a set lookup. Second, those three sets are exactly the state of lesson 0007: everything about the past that the future depends on. The recursion carries it down and the undo line restores it on the way back up.

Say this before writing a backtracking solution

What is one decision? What is the smallest state that tells me whether the next decision is legal? Can I check legality before recursing, so a dead partial answer never gets extended? And what do I have to undo on the way out?

Why pruning is the whole point

Generate-all-then-filter and backtracking find the same 92 placements on an empty board. They do not do the same work. Measured on this machine, empty 8×8 board:

Counting all 8-queens placements, empty board
All 8! permutations, then filterBacktracking with the check
Nodes visited109,6012,057
Wall time97 ms4 ms

109,601 is every partial row-assignment of every length (the whole permutation tree). Backtracking visits about 2,000 of them, because the moment the third queen lands on a diagonal with the first, that entire subtree — every way of placing the remaining five — is skipped. Same output, roughly a fifty-fold smaller search. Reading the bound still matters, as in lesson 0001; pruning is what lets the same bound hold when it is a little less friendly (n=12, say).

The bug that passes the sample. Leave out the three remove calls. Nothing crashes; the first queen’s row and diagonals stay “taken” for every later branch, so the search quietly misses valid placements. On 2,000 random 6×6 boards with reserved squares it disagreed with a brute-force count on 30.9% of them; the version with the undo line agreed on all 2,000. The failure is in state that leaks between sibling branches, and it is only visible against a reference. (Same family as the lesson 0008 post-order bugs: the recursion is right, the bookkeeping is not.)

Saying it out loud

"Eight by eight, count placements where no two queens attack. Tiny
 bound, so exponential is allowed, and two queens can't share a
 column, so I place one per column and only choose the row - that's
 at most 8 factorial. Better: the conflicts are checkable as I go.
 State is three sets: taken rows, taken r+c diagonals, taken r-c
 diagonals. For each column I try each row, skip it if it's reserved
 or conflicts, otherwise add it to the sets, recurse, and remove it.
 Checking before the recursive call prunes whole subtrees - about
 two thousand nodes instead of a hundred thousand.

 If the bound were 40 and the problem a subset sum, I'd stop: 2^40
 leaves and nothing prunes early, so that's a table, not a search."
