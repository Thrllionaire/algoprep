The Shape of the Answer

The budget told you what you cannot afford. Now count how many candidates there are — and the gap between those two numbers names the technique.

Lesson 0001 gave you a budget from the input. But a budget eliminates; it does not choose. The second question is asked of the answer, not the input: what shape is the thing I am looking for, and therefore how many of them exist? Divide the search space by the budget and the machinery is forced.

Count the candidates

Five shapes cover almost everything. Each has a candidate count you can derive in your head — and you should derive it, not memorise it, because the derivation is what transfers:

The counts follow from one-line arguments, which is why this is worth deriving rather than remembering. See the glossary for exact definitions of subarray, subsequence and subset — the distinction is the whole lesson.

Note that "subarray" and "substring" mean the same thing — one for arrays, one for strings. Both are contiguous. "Subsequence" is the one that is not, and the two words differ by three letters while their search spaces differ by an exponential.

Divide, and the machinery is forced

Here is the move. You have a budget from the constraints and a candidate count from the shape. Compare them:

Candidates ≈ budget

Just enumerate. A contiguous shape with n ≤ 7500 gives ~2.8×107 candidates against an O(n²) budget. Two nested loops is the intended answer, and reaching for something cleverer is a mistake. Most people never realise brute force was permitted.

Candidates ≫ budget, polynomially

You cannot visit the candidates, so visit the boundaries instead. A contiguous shape at n = 105 has 5×109 candidates against an O(n) budget. Only two escapes exist: sweep a boundary pair forward so each index moves n times total (sliding window), or find an identity that collapses a whole range into arithmetic (prefix sums). That is the entire contiguous toolkit, and choosing between those two is the next section.

Candidates exponential, budget polynomial

Dynamic programming, necessarily. A subsequence shape has 2n candidates; if n = 2500 and the budget is O(n²), you are not enumerating anything. You must be indexing subproblems by position and reusing them. This is why "longest increasing subsequence" is DP and "longest increasing subarray" is a one-line scan — the shape, not the wording, decided it.

Candidates exponential, budget exponential

Enumerate deliberately. If n ≤ 20 the bound is inviting you to walk all 2n subsets (bitmask), and if n ≤ 10, all n! arrangements (backtracking). You met this as the neon-sign tell in lesson 0001; now you know what it is a sign of.

Within a shape, the return type picks the tool

Shape fixes the search space. What the problem asks you to return — a yes/no, a count, an optimum, or the winning object itself — fixes how you traverse it. Explore the intersections; do not try to memorise this grid. It is a lookup surface, and the two paragraphs after it are the part worth internalising.

Two things to take from the grid rather than the grid itself. First: the return type usually changes only the bookkeeping. "Find the longest window" and "return the longest window" are the same algorithm plus two stored integers. Second: one cell is genuinely different from its neighbours — contiguous + count. That one is worth a section.

The one contrast to internalise: window vs. prefix sum

Both are O(n). Both work on contiguous runs. Choosing wrong does not make your solution slow — it makes it silently incorrect, which is far worse in an interview. The governing rule is monotonicity:

A two-pointer sweep is valid only when "movement in one direction should not reverse the effects of movement in the other direction." — USACO Guide

With all-positive values that holds: growing the window can only raise the sum, shrinking it can only lower the sum. So a window handles "longest run with sum at most k" perfectly:

def longest_at_most(nums, k):          # all values positive
    left = total = best = 0
    for right, v in enumerate(nums):
        total += v
        while total > k:               # safe: every removal lowers total
            total -= nums[left]
            left += 1
        best = max(best, right - left + 1)
    return best

Allow a single negative number and the guarantee dies — removing an element can now raise the sum, so shrinking is no longer safe, and left can never move back to recover. Here is the smallest counterexample, which is worth keeping in your head:

nums = [1, -1, 0],  k = 0

The whole array sums to 0, so the true answer is 3.
The window above returns 2: at right = 0 the sum is 1 > 0, so it
shrinks past index 0 — and can never come back for it.

When monotonicity is absent, or the question is "exactly k" rather than "at most k", you stop sweeping boundaries and start doing arithmetic. The identity sum(l..r) = p[r] − p[l−1] holds no matter the signs, so rearranging it turns the question into a lookup:

from collections import defaultdict

def count_exactly(nums, k):            # negatives are fine
    seen = defaultdict(int)
    seen[0] = 1                        # the empty prefix
    running = count = 0
    for v in nums:
        running += v
        count += seen[running - k]     # every earlier prefix p with running - p == k
        seen[running] += 1
    return count
Both functions above were property-tested against brute force on thousands of random inputs before being published here — longest_at_most on positive values only, which is precisely the limit of its claim, and count_exactly on inputs including negatives.

Nothing shrinks; nothing needs to. That is why this technique is immune to sign. The counting-with-a-map idea is exactly how the USACO Guide solves CSES Subarray Sums II: "at each index i, we can count the number of prefixes with sum equal to prefixSum[i]−x". And the maximum-subarray case is the same sweep tracking a running minimum prefix (USACO Guide), which is Kadane's algorithm wearing different clothes.

The decision, in one line

Contiguous and the predicate only ever tightens as the window grows → window. Contiguous and you need an exact value, or values can be negative → prefix sums plus a hash map.

Saying it out loud

Stack this on top of lesson 0001's opening. Two sentences, before any code:

"n is 10^5, so I need n log n or better — no enumerating pairs.
 And the answer is a contiguous run, of which there are about
 5×10^9, so I can't visit candidates at all; I need either a
 forward sweep or a prefix-sum identity. The predicate here only
 tightens as the window grows, so a sliding window is valid.
 If negatives were allowed I'd switch to prefix sums, because
 shrinking would stop being safe."

That last sentence is the one that reads as senior. You are not just choosing a technique; you are naming the condition under which your choice stops being correct. Very few candidates volunteer that, and it is the difference between having memorised a pattern and understanding it.

Where this fails. The shape is not always stated. "Pick some of the items" could be a subset or a subsequence, and you have to ask whether order matters — which is itself a good clarifying question. Greedy also cuts across the whole grid: it is less a shape than a proof obligation, and it belongs in its own lesson rather than a cell. And the counts here assume the shape is over the whole input; problems with extra structure (already sorted, bounded values, a tree instead of an array) can beat them.
