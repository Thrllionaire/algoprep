Recursion, Memo, Table

Three things that look like separate topics on a syllabus — recursion, memoization, dynamic programming — are one idea, written three ways. This lesson writes the same function all three ways and watches the runtime change by six orders of magnitude while the answer never does.

The coin problem. Given coin denominations you can reuse as many times as you like, and a target sum x, find the minimum number of coins that sum to x. With coins = [1, 3, 4] and x = 10, the answer is 3: 3 + 3 + 4.

The recursive idea, first

Whatever coin you spend first, the rest of the problem is the same problem, smaller. Call solve(x) the fewest coins needed for sum x. Picking coin c first leaves solve(x - c) to solve, plus the one coin you just spent — and you want the best choice of c, so:

The recurrence

solve(x) = min over every coin c of ( solve(x − c) + 1 ), with base case solve(0) = 0 and solve(x) = ∞ for x < 0.

That sentence translates line for line into code — this is what "formulate the problem recursively" means in practice, and it's worth doing before writing anything that runs fast.

def solve_naive(coins, x):
    if x < 0:
        return float('inf')
    if x == 0:
        return 0
    return min(solve_naive(coins, x - c) + 1 for c in coins)
Competitive Programmer's Handbook, ch. 7, uses this exact problem to introduce dynamic programming, and states the general principle behind it plainly: "the idea in dynamic programming is to formulate the problem recursively so that the solution to the problem can be calculated from solutions to smaller subproblems."

The one thing wrong with it

solve_naive is correct on every input. It is also catastrophically slow, and the reason has a name already in the glossary: dynamic programming solves problems by combining answers to smaller overlapping subproblems — the defining feature is overlap. solve(6) gets asked for by the branch that spent a 1 first and the branch that spent a 4 first. Plain recursion answers it twice, from scratch, both times — and every subproblem below it twice again, and so on down.

Measured, not estimated: instrumenting solve_naive with a call counter, for coins = [1, 3, 4]: solve_naive(10) makes 313 recursive calls. solve_naive(20) makes 38,446. solve_naive(30) makes 4,728,718 — for a function that only ever returns one of about thirty distinct answers. The overlap is being paid for again at every single visit.

Memoization: pay for each answer once

The fix does not touch the recurrence at all. It only changes what happens the second time solve is asked the same question: check a cache first, and only do the work if the answer isn't already sitting there.

def solve_memo(coins, x, memo=None):
    if memo is None:
        memo = {}
    if x < 0:
        return float('inf')
    if x == 0:
        return 0
    if x in memo:
        return memo[x]
    memo[x] = min(solve_memo(coins, x - c, memo) + 1 for c in coins)
    return memo[x]

Same measurement, memoized: solve_memo(30) makes 91 recursive calls, not 4,728,718 — because each of the 31 distinct sums from 0 to 30 is now computed exactly once. The recurrence, the base cases and the answer are all identical to solve_naive; only the number of times each subproblem gets solved changed.

The invariant

Before solve_memo(x) returns, memo[x] holds the correct answer for x — and every future call with that same x returns it without recursing again. Memoization is this one promise, nothing more: never solve the same state twice.

Tabulation: the same promise, built bottom-up

solve_memo discovers which states it needs on the way down and fills them in on the way back up, in whatever order recursion happens to visit them. Nothing stops you filling the same table in a plain loop, smallest state first, since solve(x) only ever needs sums smaller than x:

def solve_table(coins, x):
    value = [float('inf')] * (x + 1)
    value[0] = 0
    for i in range(1, x + 1):
        for c in coins:
            if i - c >= 0:
                value[i] = min(value[i], value[i - c] + 1)
    return value[x]

Same recurrence, same base case, same answer — now with no recursion, no call stack, and no function-call overhead per state. CPH is direct about the trade: "most competitive programmers prefer this implementation, because it is shorter and has lower constant factors. … Still, it is often easier to think about dynamic programming solutions in terms of recursive functions." Think in recursion, ship the table.

Property-tested against each other — solve_memo and solve_table compared on 2,000 random small coin sets and target sums: 0 disagreements. They're the same function; only the order of evaluation differs.

Naming the state

Every one of the three functions above takes the same one piece of information: x, the sum still left to form. That's the state — the smallest description of "where you are" from which the rest of the problem is determined. Get the state right and the recurrence, the memo key, and the table's index are all the same thing, decided once. Miss part of the state — forget that a later problem might also need to know, say, how many coins have been used so far — and the same input gets treated as two different states that happen to look identical, which is a silent correctness bug rather than a slow program.

Practice

Commit to an answer before revealing the options.

Saying it out loud

"This wants an optimum built from smaller versions of the same
 problem, so I'll formulate it recursively first: solve(x) is the
 best answer for state x, defined in terms of solve at smaller states.

 Before I worry about speed, I check for overlap - do multiple paths
 through the recursion ask for the same state? Here, yes: spending a 1
 first and a 4 first both eventually ask for solve(6). That overlap is
 the whole justification for memoizing rather than just recursing.

 I'll think it through recursively, then ship it as a bottom-up table
 over states 0 to x, since that's the same computation with lower
 overhead and no recursion depth to worry about.

 The state is just x, the sum left to form - that's what has to be the
 memo key and the table index, nothing more and nothing less."

The sentence worth saying to an interviewer is "here's the recurrence and here's why the subproblems overlap" — not "I'll use DP." Naming the overlap is what proves memoization will help before you've spent time coding a naive version that would run for a very long time on any real input.
