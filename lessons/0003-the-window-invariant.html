Lesson 0003 · algoprep

The Window Invariant

You can spot a window problem now. This is the lesson where you stop getting the shrink condition wrong — by writing one sentence before you write the loop.

Lessons 0001 and 0002 attacked the first failure mode: not knowing which family a problem belongs to. This lesson attacks the second one you named — right pattern, wrong details. Nearly every window bug is one of three: the while condition is backwards, the answer update sits in the wrong place, or the bounds are off by one. All three have the same cure, and it is not memorising templates.

The skeleton is mostly blanks

Every same-direction window looks like this. The shape is never the hard part:

left = 0
for right in range(n):
    include(arr[right])       # 1. what state does the window carry?
    while ???:                # 2. when does left have to move?
        exclude(arr[left])    # 3. how do I undo an inclusion?
        left += 1
    ???                       # 4. where does the answer get updated?

Blanks 1 and 3 are mechanical — whatever you add, you must be able to subtract. Blanks 2 and 4 are where solutions go wrong, and both are decided by the same sentence.

Write the invariant, and blank 2 fills itself

An invariant is a claim that is true every time control reaches a particular line. For a window, write it about the line just after the shrink loop:

The invariant, for a longest-window problem

When control reaches the update, [left, right] is the longest window ending at right that satisfies the predicate.

Now notice what the shrink loop is for. Growing the window by one element may have broken that claim. The loop's entire job is to restore the invariant. So the while condition is not a thing to recall — it is whatever says "the claim is currently false":

from collections import defaultdict

def longest_k_distinct(s, k):
    count = defaultdict(int)
    left = best = 0
    for right, ch in enumerate(s):
        count[ch] += 1
        while len(count) > k:              # the claim is false: too many distinct
            count[s[left]] -= 1
            if count[s[left]] == 0:
                del count[s[left]]         # or len(count) stops meaning "distinct"
            left += 1
        best = max(best, right - left + 1) # claim restored, so measure here
    return best

And blank 4 follows too. The invariant tells you the window is valid at that line and nowhere else, so that is the only line where measuring it is meaningful. Put the update inside the shrink loop and you would be measuring windows the invariant says nothing about.

The del matters more than it looks. len(count) is standing in for "number of distinct characters", and a key left behind with value 0 quietly breaks that correspondence — the window then reports more distinct characters than it holds and shrinks too far. This is a textbook case of the code drifting from the invariant while still looking right.

The inversion: shortest windows shrink the other way

Here is the detail that catches almost everyone. Ask for the shortest valid window instead of the longest and the while condition flips to its opposite:

def shortest_at_least(nums, target):       # positive values
    left = total = 0
    best = float('inf')
    for right, v in enumerate(nums):
        total += v
        while total >= target:             # while the claim is TRUE
            best = min(best, right - left + 1)   # measure before losing it
            total -= nums[left]
            left += 1
    return 0 if best == float('inf') else best

Both loops are correct. They differ because shrinking is playing a different role in each:

The line worth keeping

For a longest window, shrinking is repair: you shrink while the window is broken, and measure once it is fixed. For a shortest window, shrinking is the search: you shrink while the window still works, measuring each time, because the last size that worked is the smallest one.

So "the update goes after the shrink loop" is not a rule — it is a consequence of which question you asked. Derive it from the invariant each time and you cannot get it backwards.

Why the nested loop is still O(n)

A while inside a for looks like O(n²), and candidates talk themselves out of a correct window over exactly this. The answer is an amortised one, and it is worth being able to say cleanly — the Competitive Programmer's Handbook files two pointers under Amortized analysis rather than under arrays, because the argument is the technique:

"While there is no useful upper bound on how many steps the pointer can move on a single turn, we know that the pointer moves a total of O(n) steps during the algorithm, because it only moves to the right." — Laaksonen, Competitive Programmer's Handbook, ch. 8

Don't count the inner loop per iteration; count left over the whole run. It starts at 0, only ever increases, and stops at n. So at most n shrink steps happen in total, however lumpy their distribution — one turn may shrink six times precisely because five earlier turns shrank none. Two pointers, n moves each, O(n).

The same book's version of this algorithm advances left in the outer loop and right in the inner one — the mirror image of the template above. Both are O(n) by the same argument. Useful evidence that the template is not sacred; the invariant is.

Trace it, don't read it

Seven turns of longest_k_distinct with k = 2. At each turn the right pointer takes in one character and you place left. One turn requires it to travel three cells at once; most require it not to move at all.

Counting: the third place an update can go

Lesson 0002 claimed the return type changes only the bookkeeping. Here is the cash value of that claim. To count windows rather than measure the best one, change one line:

        total += right - left + 1     # in place of best = max(...)

Why that number? With the invariant restored, [left, right] is valid — and so is every window inside it that ends at right: [left+1, right], [left+2, right], … [right, right]. That is right - left + 1 windows, and nothing starting before left qualifies. Every valid window gets counted exactly once, at its own right endpoint.

This step hides a condition. It assumes every sub-window of a valid window is also valid — true for at most k distinct, false for at least k distinct. When it fails, count the complement instead and subtract from the n(n+1)/2 total. Naming this condition unprompted is a strong signal; most candidates write the line as a memorised incantation.

And once you can count at most k, you get exactly k free, by subtraction rather than by a cleverer window:

def count_exactly_k_distinct(s, k):
    return at_most(s, k) - at_most(s, k - 1)

Every subarray with at most k distinct characters has either exactly k, or at most k−1; subtract and only the first group survives. Two O(n) passes. This matters because a direct "exactly k" window does not work — the predicate is not monotonic in the window's length, and the next section shows exactly what that looks like. (Guard at_most to return 0 when k < 0, or the k = 0 case reaches for a negative budget.)

All four functions in this lesson were property-tested against brute force on 30,000 random inputs each before publishing — 120,000 comparisons, no disagreements. shortest_at_least was tested on positive values only, which is the exact limit of its claim.

Is the window even legal? The predicate, and monotonicity

Every section above assumed a window was allowed here. Two words have been carrying that assumption, and an interviewer can ask you to define either one.

The predicate is the yes/no test a window must pass. It is not the invariant: the invariant is a claim about where the pointers have come to rest, and the predicate is the test that claim refers to. Each function above has exactly one, and it is one line:

len(count) <= k        # longest_k_distinct
total >= target         # shortest_at_least

That line is what blank 1 must track and what blank 2 must negate. Name the predicate and both blanks are already decided — which is why "what is the predicate?" is the first question, not "which template is this?"

The promise the forward-only sweep needs

left never goes back. That is the entire source of the O(n), and it is not a free choice — it is a bet that the boundary between invalid and valid starts never moves backwards as right advances. The bet pays off exactly when the predicate is monotonic in the window's growth:

Monotonic, stated so you can test it

Grow the window and, once the predicate turns false, it stays false. It may never come back. Equivalently, for each right the valid starts form one unbroken run ending at right — so there is a single boundary, and left is it.

"Movement in one direction should not reverse the effects of movement in the other direction." — USACO Guide, Two Pointers

Test it the cheap way: fix the left end, grow the right end one element at a time, and watch the predicate. Two arrays, same predicate shape, opposite verdicts:

The only difference is a negative number. Adding an element to a window of positives can only raise the sum, so sum <= k breaks once and stays broken. Adding to a window with negatives available can lower it, so the predicate un-breaks — and an un-breaking predicate has no single boundary to put left on.

What the broken promise actually costs

Run the longest-sum-at-most-k window on [1, -1, 0] with k = 0 and watch it go wrong in three turns:

right=0   total=1   1 > 0, so shrink: drop nums[0]  →  total=0, left=1
                    window is empty, best=0
right=1   total=-1  valid, left holds  →  window [-1],     best=1
right=2   total=-1  valid, left holds  →  window [-1, 0],  best=2

returns 2   —   but [1, -1, 0] itself sums to 0, so the answer is 3

The failure is precise, and it is not an arithmetic slip. At right = 0 the only window available was [1], which is invalid, so the shrink loop pushed left to 1. At right = 1 the best start is index 0 — behind where left now sits. The boundary moved backwards, from 1 to 0, and left cannot follow it. Every element it walks past is given up permanently, which is fine when the boundary only ever advances and fatal when it does not.

And it fails loudly, not rarely. On [3, -3, 2, -4, -2, -3, -1, -2] with k = -5, the whole array sums to −10 and is valid, so the answer is 8. The window returns 0 — it reports that no valid subarray exists at all. Across 30,000 random small arrays containing negatives, this window disagreed with brute force 30.2% of the time; on 30,000 all-positive arrays, never once. A wrong window is not a near miss you can patch with an off-by-one fix.

The second way it breaks: a band instead of a run

Negatives kill monotonicity by letting a false predicate turn true again. Exactly k kills it differently, and this is what the subtraction trick above was quietly working around. Take s = "aabbc", predicate exactly 2 distinct, and fix right = 4, walking the left end outwards:

The valid starts are {2, 3} — a band with invalid windows on both sides, because growing the window past a third character breaks the predicate while shrinking it below two breaks it as well. Two boundaries; left is one number and cannot mark both. This is the whole reason at_most(k) - at_most(k-1) exists.

The two-question licence check, before you write any window

1. What is my predicate, written as one expression over the window's state?

2. If growing the window makes it false, can growing it further make it true again? If yes, I do not get a window — say so out loud and reach for prefix sums.

The shortcut, once you trust it: predicates built from quantities that only move one way as elements enter — a count, a distinct count, a sum of non-negatives — are monotonic, so at most and at least over them are safe. Mixed-sign sums and the word exactly are the two tells that they are not.

Every number in this section is generated, not asserted: the three-turn trace, both boundary tables, the 8-element case and the 30.2% figure all come from running the published code against brute force over every subarray. The disagreement rate is deliberately included — "this is wrong in theory" persuades nobody, and "this is wrong on a third of random inputs" ends the argument.

Practice

Six questions. Two reach back to lessons 0001 and 0002, because nothing tells you in an interview which lesson a problem came from.

Saying it out loud

Stack this onto the triage sentences from the first two lessons. Note that it opens with the licence check — monotonicity first, invariant second. Say it before writing the loop, because it is also how you avoid the bug:

"This is a contiguous shape asking for a longest, and the predicate
 only tightens as the window grows, so a sliding window is valid.

 My invariant: when I reach the update line, [left, right] is the
 longest window ending at right with at most k distinct characters.
 So the while condition is 'more than k distinct' — that's the
 invariant being false — and the update goes after the loop, because
 that's the only point where I know the window is legal.

 The nested while is still O(n): left only moves forward, so at most
 n shrink steps happen across the whole run."

Three things are doing work there. You named the invariant before coding, so the interviewer can check your reasoning rather than your typing. You derived the loop condition instead of recalling it. And you pre-empted the complexity question they were about to ask.

Where this fails. Fixed-size windows have no shrink loop at all — you evict exactly one element per step, so the while becomes an if and the invariant is about size rather than a predicate. Windows over a maximum or minimum need a monotonic deque, because those cannot be undone by subtraction: blank 3 of the skeleton has no cheap answer. And a predicate that is not monotonic in window length (exactly k distinct, or any mixed-sign sum) has no single resting place for left — see the licence check, the one part of this lesson to run before deciding the problem is a window at all.
