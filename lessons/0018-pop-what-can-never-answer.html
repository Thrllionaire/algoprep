Pop What Can Never Answer

Some problems ask, for every position in a sequence, about the nearest element to its right that beats it — the next warmer day, the next taller building, the next larger price. Checking rightwards from every position is quadratic. The fix is to keep a stack of positions still waiting for an answer, and to notice that the moment a new element arrives, it settles every waiting position it beats — and nothing else is worth keeping out of order.

The tell is “for each element, find the nearest one to the left or right that is larger (or smaller),” with n up to 105, so a scan-right from every position is off the table. Close cousins: “how many days until…,” “span of consecutive days,” “largest rectangle in a histogram.” If the question is about a window of fixed width instead, that is lesson 0003's territory.

The quadratic version, and why it's wasteful

Daily Temperatures (LeetCode 739): for each day, how many days until a strictly warmer one, or 0 if none. For [73, 74, 75, 71, 69, 72, 76, 73] the answer is [1, 1, 4, 2, 1, 1, 0, 0]. The obvious code scans right from each day. Per lesson 0001, n = 105 allows roughly O(n log n), not O(n²). And the waste is visible: when day 5 (72) looks right, it re-reads days that days 3 and 4 already read.

The stack of days still waiting

Walk left to right, keeping a stack of day indices that have not yet found a warmer day. Each new temperature t answers every waiting day colder than it. Because we pop only while the top is colder, the temperatures on the stack are always non-increasing from bottom to top — that is the “monotonic” (see the glossary). The USACO Guide states the reason a waiting element can be discarded: “the pair containing value will never be the solution to any index j>i, since ai is less than or equal to value and has an index further to the right.” Here, a colder day buried under a warmer one can never be anyone's nearest warmer day first.

def next_warmer(temps):
    ans = [0] * len(temps)
    stack = []                       # indices still waiting; temps[] non-increasing
    for i, t in enumerate(temps):
        while stack and temps[stack[-1]] < t:
            j = stack.pop()
            ans[j] = i - j           # day i is j's first warmer day
        stack.append(i)
    return ans

Each index is pushed once and popped at most once, so the loop does at most 2n stack operations no matter how the inner while looks — O(n) overall, amortised (the same “each pointer moves forward only” argument as lesson 0003's window). Measured on 2,000 strictly decreasing temperatures, the worst case for the scan-right version: 1,999,000 comparisons for the quadratic code, 2,000 loop steps for the stack. Honest nuance: on 2,000 random temperatures the quadratic code only needs about 14,000 comparisons, because a warmer day usually turns up quickly. The stack's advantage is the guarantee, not the average.

Say this before writing a monotonic stack

Am I asked, per element, for the nearest larger or smaller neighbour on one side? If so: a stack of positions still waiting, popped by each new arrival that beats them. Which direction I sweep and which comparison I pop on come from the question — and whether ties count.

The one-character bug: < versus <=. Change the pop test to temps[stack[-1]] <= t and the code looks identical, runs just as fast, and answers the wrong question — it resolves a day with the next equal-or-warmer day, not strictly warmer. Measured on 20,000 random arrays of 1–9 values drawn from 1–5 (so ties are common), the <= version disagrees with brute force on 13,157 — 65.8%. The correct version disagreed on 0. Read the problem for “strictly” before choosing.

Checked against a slower, honest reference

next_warmer was run against the scan-right brute force on 20,000 random small arrays with heavy ties. 0 of 20,000 disagreed.

Saying it out loud

"For each element, nearest larger neighbour on one side, n up to 1e5 -
 scanning right from every position is quadratic, so that's out.

 I keep a stack of positions still waiting for an answer. Each new
 value pops every waiting position it beats and gives them their answer;
 then it joins the stack. The stack stays non-increasing, so the top is
 always the next one a bigger value will settle.

 Each index is pushed once and popped once, so it's O(n) overall.
 And I check 'strictly' against the problem - pop on < or <= decides
 whether ties count."
