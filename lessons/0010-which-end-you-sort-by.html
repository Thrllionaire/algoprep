Which End You Sort By

Two interval problems look almost identical — a list of [start, end] pairs, sorted once, then swept left to right. They ask different questions, and the entire difference between a correct answer and a wrong one is which of the two numbers in each pair you sort by.

An interval problem you're handed a full list for, up front, never needs a heap. Lesson 0009's tell was whether the collection kept changing while you were being asked questions about it. Here it never does — every interval exists before you write a line of code — so you get to commit to one global order and sweep once, left to right, never revisiting a decision. The only choice left is which order.

Why sorting is (almost) the whole algorithm

A greedy algorithm picks the locally-best option at each step and never looks back. That is only safe when there is a proof that the local choice cannot cost you anything later — and for intervals, sorting is usually what makes that proof possible in the first place. "A greedy algorithm chooses the best move at each individual step," and interval problems are exactly where "greedy problems typically involve sorting" as their setup step (USACO Guide). Once the list is sorted, one pass is enough: no data structure has to support removing something out of order, because the order was decided in advance.

Say this before touching an interval problem

Is the whole list handed to me now, or does it keep arriving? If it's handed to me now — which every problem in this lesson is — then I sort once, by whichever end the question is actually about, and sweep. No heap, no re-sorting, no going back to an earlier decision.

Keep as many as you can — sort by end

LeetCode 435, Non-overlapping Intervals asks: given a list of intervals, what is the fewest you must remove so none of the rest overlap? Equivalently — and this is the easier way to think about it — how many can you keep, at most, with no two overlapping?

The instinct is to sort by start time, taking whichever interval begins soonest. That is wrong, and the USACO Guide's proof is worth reading in full, because it is a real exchange argument rather than an assertion: sort by end time instead, and always keep the next interval whose start is no earlier than the end you're currently holding.

# LC 435 — greedy, sorted by END time
def erase_overlap_intervals(intervals):
    if not intervals:
        return 0
    intervals = sorted(intervals, key=lambda iv: iv[1])
    keep = 0
    last_end = float('-inf')
    for start, end in intervals:
        if start >= last_end:
            keep += 1
            last_end = end
    return len(intervals) - keep   # removals = total - kept

The proof for sorting by end, quoted directly rather than paraphrased: "If we have two events E₁ and E₂, with E₂ ending later than E₁, then it is always optimal to select E₁. This is because selecting E₁ gives us more choices for future events... the set of events that can go after E₂ is a subset of the events that can go after E₁." (USACO Guide) Whatever you could still fit after the later-ending interval, you could also still fit after the earlier-ending one — so the earlier end is never a worse choice, and picking it first can only leave you more room, never less.

Union them into their coverage — sort by start

LeetCode 56, Merge Intervals asks a different question entirely: not how many to keep, but what is the minimal set of intervals that covers the exact same ground as the original list. Two intervals overlap once the later-starting one begins no later than the earlier one's end — so once the list is sorted by start, an overlap with the interval you're currently building can only be checked against that one running interval, never anything further back.

# LC 56 — sorted by START time
def merge(intervals):
    if not intervals:
        return []
    intervals = sorted(intervals)          # sorts by start, then end
    merged = [list(intervals[0])]
    for start, end in intervals[1:]:
        if start <= merged[-1][1]:
            merged[-1][1] = max(merged[-1][1], end)
        else:
            merged.append([start, end])
    return [tuple(m) for m in merged]

No single high-trust source states that overlap condition outright — it's derived here from the definition of overlap, the same call as lesson 0003's exactly(k) identity and lesson 0009's heap inversion. It is property-tested against a brute-force pairwise-overlap check (union-find over every pair) on 5,000 random small interval lists, 0 disagreements. Logged in Resources.

 Same input shape, same "sort once, sweep once" skeleton, opposite sort key — because the two questions are asking about different endpoints of the same pairs.

Swap the key on either one and it breaks — measured, not asserted. Solve LC 435 by sorting on start instead of end: it disagrees with a brute-force search over every subset on 16.0% of 2,000 random small interval sets, keeping on average about one fewer interval than the true optimum whenever it's wrong. Solve LC 56 by sorting on end instead of start: it disagrees with the union-find brute force on 15.3% of 5,000 random trials. Two different problems, two different failure shapes, strikingly similar wrongness rates — because both mistakes come from the same root cause: sorting by the endpoint the question isn't actually about.

What the constraint bound does not tell you here

Lesson 0001's constraint ladder reads n for a time budget, and an interval problem's n ≤ 10^5 just confirms O(n log n) is fine — it doesn't distinguish these two problems at all, because both are the same complexity. The distinguishing read is entirely in the return type: a count or a yes/no pulls toward the sort-by-end greedy-selection family; the object itself — the merged list, or something built from surviving intervals — pulls toward sort-by-start and a running merge. That's lesson 0002's return-type axis, doing real work again on a shape it wasn't originally built for.

Saying it out loud

"I've got a list of intervals, handed to me complete - so no heap,
 no live structure. I get to sort once and sweep.

 The question is which end to sort by. If I'm counting how many
 I can keep without overlap, that's about how much room survives -
 sort by END, always keep the interval that starts no earlier than
 my last kept end.

 If I'm merging into coverage - the object itself, not a count -
 that's about what still needs folding into what's already open -
 sort by START, and only the running interval's end can still grow.

 Sorting by the other field doesn't crash. It just answers a
 question nobody asked, and it's wrong on roughly one interval set
 in six."

The sentence worth having ready is "which end does the question actually turn on" — it is the one-line version of the whole lesson, and it is a question a sorted-array problem never has to ask, because there's only one end to sort by.
