The Constraint Ladder

Read the bound, get the budget, eliminate the families that cannot fit.

The ladder

Figures from the USACO Guide's complexity table, which assumes roughly 108 simple operations per second (“a conservative estimate … but it could be closer to 5·108 given good constant factors”). The right-hand column is ours.
Up toSlowest affordableWhat lives at that budget
n ≤ 10O(n!) Every ordering. Permutation backtracking.
n ≤ 20O(2n·n) Every subset. Bitmask DP, subsets, backtracking.
n ≤ 80O(n4) Four nested loops. Rare.
n ≤ 400O(n3) Interval DP, Floyd–Warshall, matrix chain.
n ≤ 7·103O(n2) 2-D DP over two sequences or a grid. All-pairs comparison.
n ≤ 7·104O(n√n) Square-root decomposition, Mo's algorithm. Not an interview shape.
n ≤ 5·105O(n log n) Sort first, heap, binary search on the answer, divide and conquer, ordered set.
n ≤ 5·106O(n) One pass: sliding window, prefix sum, two pointers, hash map, monotonic stack, greedy, Kadane.
n ≤ 1018O(log n), O(1) Binary search, closed-form maths, bit tricks, fast exponentiation.

The tells

n ≤ ~20. A neon sign for exponential. Nothing else needs a bound that small. Think subsets, bitmask, or "try every assignment". If you are reaching for a clever polynomial trick at n = 18, you have misread the problem.

n ≤ ~400. Cubic is on the table, which in practice means interval DP (dp[i][j] plus a split point k) or all-pairs shortest paths.

Two sequences, each ≤ ~103. Quadratic table over the pair. Edit distance, LCS, and their relatives.

n = 105 (the single most common bound). O(n log n) is the ceiling, so a nested loop is dead on arrival. Sort, heap, binary search, or a single clever pass.

n ≥ 109. You cannot even touch every element, so the answer cannot involve iterating the input. Binary search on the answer, maths, or bit tricks.

"modulo 109+7". The answer is a count so large it overflows, which means you are counting without enumerating. Counting DP, near-always. Enumeration is not just slow here, it is the wrong shape.

Values are bounded but n is not. 0 ≤ nums[i] ≤ 100 with huge n invites counting sort, a frequency array, or DP over the value range rather than the index range.

Sorted input, or "find the k-th". Sortedness is never decoration. It is there for binary search or two pointers.

Interviewer gives no constraints. Ask. "What's the rough size of n?" is a signal of seniority, not ignorance, and the answer collapses your search space.

How to use it in the room

  1. Read the constraints before the problem body.
  2. Find your budget on the ladder. Say it out loud: "n is 105, so I need n log n or better — a nested loop is out."
  3. Cross off every family above that row.
  4. Now read the problem, choosing only among what survived.

Where this fails. The ladder is necessary, not sufficient: it narrows the field, it does not pick the winner. Several families share a budget — at O(n) you still have to choose between sliding window, prefix sum, and a monotonic stack. And the figures are judge-calibrated; a human interviewer cares whether your reasoning is sound, not whether you clear a 2-second wall. The constant-factor claim is also genuinely approximate, as the source itself says.
